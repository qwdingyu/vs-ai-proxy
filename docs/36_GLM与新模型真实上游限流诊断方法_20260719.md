# GLM 与新模型真实上游限流诊断方法

日期：2026-07-19

本文记录 `UseAI - glm-5.2` 真实上游测试过程，并把方法固化为后续 GLM 新版本、其它新模型或新 provider 发布前的通用诊断流程。

## 1. 结论

`UseAI - glm-5.2` 在短时间连续请求时会出现上游限流：

- 直接请求 UseAI 上游可返回 `429`。
- 代理会把该错误归类为 `error_code=upstream_rate_limit`，用户文案为“请求过于频繁”。
- 冷却后只经过代理请求，30KB 与 673KB 请求均可成功返回 `200`。
- 代理没有异常放大请求体：673100 bytes 进入代理，673104 bytes 发给上游，仅多 4 bytes。

因此，本次日志中的 `请求过于频繁` 不是 GLM 请求转换错误，也不是代理把模型路由错了；更符合 UseAI / 上游模型短窗口频率限制。

## 2. 已验证事实

实测模型：

```text
provider_id=useai
display_provider=UseAI
model=glm-5.2
requested_model="UseAI - glm-5.2"
upstream=glm-5.2
```

实测结果：

| 场景 | 结果 | 说明 |
| --- | --- | --- |
| 673KB 直连 UseAI | HTTP 429 | 上游自身限流 |
| 30KB 直连成功后立刻走代理 | 代理 HTTP 502 / `upstream_rate_limit` | 连续请求触发短窗口限流 |
| 冷却后只走代理 30KB | HTTP 200 | 代理路由和协议处理正常 |
| 冷却后只走代理 673KB | HTTP 200 | 大请求可通过，代理无异常放大 |

成功代理日志示例：

```text
POST /v1/chat/completions - 200 (...) provider=useai requested_model="UseAI - glm-5.2" upstream=glm-5.2
```

结构化日志关键字段：

```text
request_bytes=673100
upstream_bytes=673104
stream_state=downstream_started
usage.source=upstream
```

## 3. 标准诊断方法

新增或复测模型时，不要临时写脚本。统一使用：

```bash
PROVIDER_ID=useai \
DISPLAY_PROVIDER=UseAI \
MODEL=glm-5.2 \
SIZES='30000 200000 673100' \
tests/model_release_diagnostic.sh
```

该入口会复用：

- `tests/large_request_matrix_diagnostic.sh`
- `tests/useai_large_request_diagnostic.sh`

输出位置：

```text
.bin/large-request-matrix/results.jsonl
.bin/large-request-matrix/summary.json
.bin/useai-large-diagnostic/result.json
```

参数说明：

| 参数 | 说明 |
| --- | --- |
| `PROVIDER_ID` | 配置中的 provider 实例 ID，例如 `useai`、`kimi`、`xiaomimimo` |
| `DISPLAY_PROVIDER` | VS 模型展示名前缀，例如 `UseAI`、`Kimi` |
| `MODEL` | 上游模型名，例如 `glm-5.2`、`kimi-k2` |
| `SIZES` | 请求体大小矩阵，建议至少包含小请求、中请求、真实问题请求大小 |
| `INJECT_MODEL_BINDING` | 默认为 `1`，临时配置里注入模型绑定；正式发布前建议用真实配置再跑一次 |
| `MODE` | `direct-proxy`、`proxy-only` 或 `direct-only`；频控严格模型建议用 `proxy-only` 复验 |
| `COOLDOWN_SECONDS` | 代理请求前等待秒数，用于避开 direct/proxy 连续测试触发的短窗口频控 |

## 4. 判定规则

### 4.1 判断是否代理问题

优先看：

```text
request_bytes
upstream_bytes
provider
requested_model
upstream
error_code
attempts_summary
```

判断：

- `direct=200` 且 `proxy=200`：上游和代理都可承载。
- `direct=429`：上游已经限流，优先按上游频控处理。
- `proxy=upstream_rate_limit` 且 `upstream_bytes - request_bytes` 很小：代理没有异常放大请求，优先按上游限流处理。
- 冷却后只走代理成功：代理路由、参数治理、流式处理基本正常。
- 冷却后只走代理仍失败，且 direct 成功：再重点排查代理转换、模型绑定、provider capability。

### 4.2 判断多个错误是否属于同一请求

必须按 `request_id` 关联，不要只看相邻时间。

例如：

```text
request_id=1784425390753636800 upstream_rate_limit
request_id=1784425400180224200 network_error
request_id=1784425400751169000 upstream_rate_limit
```

这是三条不同请求。VS/Copilot 可能短时间连续发送、取消或重试；不同 `request_id` 的错误不能合并成一个“代理重试链”结论。

### 4.3 判断 direct/proxy 连续测试是否触发限流

`useai_large_request_diagnostic.sh` 默认先 direct 再 proxy。对于频控严格的模型，这本身就是两次连续请求，可能出现：

```text
direct=200
proxy=upstream_rate_limit
```

这不一定说明代理有 bug。必须等待 15-30 秒后，再单独只跑代理请求验证。

标准复验命令：

```bash
PROVIDER_ID=useai \
DISPLAY_PROVIDER=UseAI \
MODEL=glm-5.2 \
SIZES='30000 673100' \
MODE=proxy-only \
COOLDOWN_SECONDS=20 \
tests/model_release_diagnostic.sh
```

## 6. 注意事项

- 不要把 `502` 直接等同于代理 bug；必须看 `error_code`。
- 不要把不同 `request_id` 的 WARN 和 INFO 当作同一次请求。
- 不要用一次 direct/proxy 连续失败直接下结论；频控模型必须做冷却后的单独代理请求。
- 不要只用 Web 测试页小请求验证 VS/Copilot 真实可用性；VS/Copilot 会携带大量工具声明和上下文。
- 不要只看 HTTP 状态码；`request_bytes/upstream_bytes` 能判断代理是否异常放大。
- `upstream_rate_limit` 属于上游或聚合商频控，代理只能诊断、冷却和提示，不能保证消除。
- 如果 `network_error` 与 `upstream_rate_limit` 混在一起，先按 `request_id` 分组，再看 `attempts_summary`。

## 7. 后续可优化方向

已完成的低风险优化：

1. `upstream_rate_limit` 的处理建议从“稍后重试”细化为“等待 15-30 秒、减少并发或切换模型”。
2. 管理页 provider health 已展示冷却剩余时间。
3. 诊断脚本已支持 `MODE=proxy-only` 与 `COOLDOWN_SECONDS`，避免 direct/proxy 连续测试误触发频控。

仍不做的高风险动作：

- 不按 `glm-5.2` 模型名写请求协议特判。
- 不自动吞掉 429 后长时间 sleep 重试，避免拖死 VS/Copilot 交互请求。
- 不在下游流已经开始后切换 provider。

这些属于体验增强，不改变本次判断：`UseAI - glm-5.2` 冷却后可通过代理成功处理 673KB 请求。
