## 三个字段的准确解释

### 有用量数据

“有用量数据”不是“请求成功率”，也不是“已经上传到某个云端”。

它的准确含义是：

> 服务商返回了 token 用量，并且本地代理成功记录的请求数 / 可统计请求总数。

例如 `7 / 184 次 (4%)` 表示 184 次请求里只有 7 次有服务商返回的用量。表里的输入、输出、总 token 都只来自这 7 次。

产品文案采用：

> 有用量数据

### 缓存命中的输入

“缓存命中的输入”来自 OpenAI 兼容 usage 的 `prompt_tokens_details.cached_tokens`。

它是“输入 Token”的子集，表示上游认为命中了提示词缓存的输入 token。

它已经包含在输入 Token 和总 Token 中，不能再额外相加。

建议产品文案改为：

> 缓存命中的输入

### 模型内部思考用量

“模型内部思考用量”来自 OpenAI 兼容 usage 的 `completion_tokens_details.reasoning_tokens`。

它是“输出 Token”的子集，表示上游把多少输出 token 标记为 reasoning / thinking token。

它已经包含在输出 Token 和总 Token 中，不能再额外相加。

当前为 0 只能说明已记录的用量里没有 reasoning_tokens，不能推出模型没有内部推理。

## 对当前统计表的正确解读

| 提供商 | 请求 | 有用量数据 | 正确解读 |
| --- | ---: | ---: | --- |
| useai | 184 | 7 / 184 (4%) | 只有 7 次请求有 token 明细，累计 token 只覆盖这 7 次 |
| kimi | 73 | 3 / 73 (4%) | 只有 3 次请求有 token 明细，累计 token 只覆盖这 3 次 |

风险：

- 覆盖率只有 4% 时，不能把总 Token 当成真实总消耗。
- 未返回用量的请求是“未知”，不是“0 消耗”。
- UI 必须提示统计覆盖率，否则用户容易误判成本。

## API-Switch / sub2api 分析结论

API-Switch 值得吸收的是：

- 对外暴露逻辑模型名，例如 `auto`。
- 对内解析为候选 provider/model。
- 手动探测和测速。
- 分组、排序和候选列表的产品形态。

但不能直接照搬，因为：

- 它更像固定优先级 failover，不是真正轮询或智能负载均衡。
- 显式 `auto` 和 fallback `auto` 的过滤路径不一致。
- 失败后的 cooldown / disable 语义容易把临时错误变成长时间不可用。

sub2api 值得吸收的是：

- sticky session。
- priority + LRU。
- load-aware 选择。
- top-K 加权，避免单一账号长期垄断。
- temp unschedulable，避免偶发错误导致永久禁用。
- channel monitor 和历史健康状态。

但不能直接照搬，因为：

- sub2api 是多租户账号池平台。
- 它包含用户、余额、计费、账号池、OAuth、支付等复杂体系。
- 当前产品定位更适合“本地/团队级 LLM 接入治理层”，不应被多租户平台复杂度拖垮。

## 产品路线判断

Lite 版本应该保持：

- 基础代理。
- Provider / 模型配置。
- 基础请求日志。
- 基础错误解释。
- 基础 token 统计。
- 手动模型测试。
- Windows exe。

Pro 版本应该形成护城河：

- 智能 Auto Router。
- Provider 健康中心。
- 参数兼容治理。
- Token 与成本治理。
- 长会话治理。
- 可解释错误诊断。

核心差异不是“支持更多 provider”，而是“在真实 AI 编程工具里稳定、可解释、低成本地用好 provider”。

- 已将“已上报 / Token 明细覆盖”改为“有用量数据”。

- 保留技术详情，但默认展示一句话结论。

验收标准：

- 前端文案不再让用户误以为 4% 是成功率。
- 单元测试继续保证 cached/reasoning 不重复计入 total。

### P1：正确的 auto 模型

- 定义 `auto`、`coding-fast`、`coding-pro` 等逻辑模型。
- 统一候选过滤：enabled、provider enabled、cooldown、capability。
- 同时记录 requested_model 和 upstream_model。
- unknown model 默认不静默 fallback，除非用户显式开启 fallback 策略。
- 每次路由输出 route decision：为什么选中，为什么跳过。

验收标准：

- 显式 `auto` 不会命中 disabled provider。
- 400/404 不被误判成渠道健康失败。
- 流式已经开始后不透明重放。

### P2：轻量健康感知路由

- 增加 health state：healthy、degraded、cooldown、probing、disabled。
- 只对 429、5xx、网络错误、上游超时进入 cooldown。
- cooldown 到期后使用单探针 half-open。
- 加入 priority + last_used 的轻量轮换。

验收标准：

- 偶发失败不会永久禁用 provider。
- 高优先级 provider 不会因为无意义轮询被打散。
- route decision 可解释。

### P3：Pro 高级能力

- 后台健康探测，带并发预算和退避。
- sticky session，适配 VS/Copilot/Codex 长会话。
- 成本/速度/稳定策略。
- top-K 加权路由。
- Token 覆盖率趋势和成本估算。
- provider compatibility profile。

验收标准：

- 用户可以知道当前选路原因。
- 用户可以知道哪个 provider 不稳定、为什么不稳定。
- 长会话和大上下文问题有 session 级别诊断。
