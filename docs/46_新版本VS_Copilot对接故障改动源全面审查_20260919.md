## 2. 发现 #1（主因，已证实）：anthropic 类型 provider 在流式路径上协议错配

### 2.1 证据链（发布版 v0.2.76 代码，可逐条复核）

1. **VS Copilot 固定 `stream=true`**。这是仓库内多处文档确认的既定事实（docs/08、docs/22、docs/25；未提交测试文件 `handler_anthropic_stream_test.go` 头部注释亦重申）。
2. 发布版 `handleChatCompletions` 的流式分支**在 anthropic 判断之前就处理并返回**（`git show v0.2.76:internal/proxy/server.go` 第 915~946 行）：`if req.Stream` 直接调用 `s.handleStream(streamWriter, streamReq, prov, req, provider.ApiFormatOpenAi)`。
3. anthropic 的专用处理（`SendAnthropicChatRequestWithPath`，OpenAI→Anthropic 请求转换、Anthropic→OpenAI 响应转换）**只存在于非流式分支**（同文件第 948~1014 行）。
4. 发布版 `handleStream`（第 1506~1531 行）只认两种上游格式：Ollama 与 OpenAI。整个 v0.2.76 的 `internal/` 中**不存在** `ApiFormatAnthropic`（`git grep 'ApiFormatAnthropic' v0.2.76` 无结果）。
5. `providerFromConfig`（第 190~213 行）把 `type=anthropic` 构造成 `*OpenAIProvider`（带 `Transport.ChatPath="v1/messages"`）；`ResolveApiFormat`（`capabilities.go:423`）对 `*OpenAIProvider` 返回 `ApiFormatOpenAi`。
6. 因此流式请求进入 `streamOpenAI` → `prov.ChatStream`（`provider.go:1246`）：用 `marshalOpenAIChatCompletionsRequest` 生成 **OpenAI 线格式请求体**，POST 到 `chatURL()` = `{base_url}/v1/messages`。上游收到的是：无顶层 `system`、无 `anthropic-version` 头、无 `x-api-key` 的 OpenAI 体。
7. 失败模式 A（绝大多数 Anthropic 端点）：上游 4xx → `streamOpenAI` 触发"流式失败转非流式"兜底（`canAttemptAlternateChatMode`）→ `prov.Chat` 再次以 OpenAI 体打 `/v1/messages` → 再失败 → 候选循环结束（防御策略只保留首选候选，`applyDefenseCandidatePolicy`）→ `writeProxyDiagnosticError(w, 502, allCandidatesFailedDiagnostic(...))`（server.go 第 1183~1188 行）。**VS 每次对话收到 502**。
8. 失败模式 B（个别宽容网关返回 200 + Anthropic event-based SSE）：OpenAI 流解析器读不到 `choices[].delta` 与 `data: [DONE]`，`event:` 行按协议应被忽略/泄漏，最终以"解析响应失败"或流中断错误收场。**VS 收到空响应或报错**。

### 2.2 症状与"测试页可用、VS 不可用"的完整解释

管理页的 provider 测试固定 `stream=false`，走的是**已正确实现**的非流式 anthropic 分支（含 `d80b7fe` 补的 `Authorization: Bearer` 头、`83c5220` 修的 chat_path 旁路），所以测试通过；VS 固定 `stream=true`，必然落入 2.1 的错误路径。两个观察互为印证，无矛盾。

### 2.3 交叉验证

- `docs/45_Anthropic类型provider流式协议错配与OpenAI兼容性核验_20260805.md`（先前排查会话产出）与本审查**独立得出的根因完全一致**（流式分支先返回、`*OpenAIProvider` 构造、`ResolveApiFormat` 误判、双向协议错配）。
- 工作区未提交的 `SendAnthropicChatStreamRequest` + `streamAnthropicAsOpenAI` 正是针对该缺陷的流式修复，`handler_anthropic_stream_test.go` 头部注释原文描述了与 2.1 相同的机理。**该修复未提交、未包含在任何已发布版本中**——发布给用户的 v0.2.76 二进制必然带此缺陷。
- 定性说明：这是 anthropic 支持（v0.2.71 新增功能）**从未在流式下工作过**的新功能缺陷，不是"原有功能被改坏"的回归。对用户而言体感相同：升级后 VS 用不了。

### 2.4 触发条件与波及面

- 触发：任一被 VS 选择的模型其候选 provider 为 `type=anthropic`。
- 不触发：所有候选均为 `openai`/`custom`/`ollama` 类型的模型——这些链路在窗口内**一行未改**（见 §8 排除项）。

## 3. 发现 #2（条件性回归，已证实）：transport 路径推导重构改变了部分自定义 base_url 的上游 URL

### 3.1 机制变化

| | v0.2.69 及以前 | v0.2.72 起 |
| --- | --- | --- |
| chat 路径事实源 | 能力注册表 `caps.ChatPath`；未知 provider 兜底 `v1/chat/completions`（`capabilityURL("chat", "v1/chat/completions")`） | **实例 `transport.chat_path` 唯一事实源**；注册表仅在实例路径为空时兜底（`chatURL()`，provider.go:1643） |
| 实例路径来源 | 不存在该字段 | `config.NormalizeProvider → normalizeProviderTransport`（config.go:229）推导并**永远填非空**：显式配置 > ollama=`api/chat` / anthropic=`v1/messages` > openai 类按 base_url 推导 |
| base_url 推导规则 | （无此概念） | 无路径 → `v1/chat/completions`；**有任意路径** → `chat/completions`（`shouldPreserveLegacyV1Path`，config.go:295） |

### 3.2 新旧 URL 逐一推演（`joinURLPath` 带重叠段去重，新旧同源）

| base_url 形态 | v0.2.69 结果 | v0.2.76 结果 | 是否变化 |
| --- | --- | --- | --- |
| `https://api.eforge.xyz/v1`（UseAI 默认） | `…/v1/chat/completions`（caps=`chat/completions` 拼接） | `…/v1/chat/completions` | **不变** |
| `https://host`（裸域名） | `…/v1/chat/completions` | `…/v1/chat/completions`（保留 legacy v1） | **不变** |
| `https://host/v1` | `…/v1/chat/completions` | `…/v1/chat/completions` | **不变** |
| `https://generativelanguage.googleapis.com/v1beta/openai`（gemini，带全路径） | `…/v1beta/openai/chat/completions` | 同左 | **不变** |
| `https://host/api`、`https://host/openai` 等非版本路径 | `…/api/v1/chat/completions`（旧逻辑无条件补 `v1/`） | `…/api/chat/completions` | **变化 → 大概率 404** |
| gemini 能力 + 裸域名 `https://generativelanguage.googleapis.com` | `…/v1beta/openai/chat/completions`（注册表路径拼接） | `…/v1/chat/completions`（推导覆盖注册表） | **变化 → 404** |

同步变化也发生在 `models` 路径上（影响模型发现 `/models`），规则相同。

### 3.3 判定

- 对"裸域名"与"/v1 结尾"两大类主流写法（含 UseAI 默认配置），**净 URL 不变**——这排除了"全体 provider 集体 404"的最坏猜想。
- 回归只发生在上表最后两行形态。docs/45 曾断言"当前用户配置里所有 provider 的 `chat_path`/`models_path` 均已显式填好，因此不构成问题"——该断言针对当时读取到的配置，本机未找到运行时 `config.json`（见 §7 自查），无法在本机复核，**保留为待现场确认项**。

## 4. 发现 #3（放大器，已证实）：配置自动迁移写回会把推导结果固化进 config.json

`f70c78e`（v0.2.70）引入的机制（config.go:504~546、592~615）：

1. `NewManager` / `Reload` 加载配置后执行 `NormalizeForRuntime`，若结果与磁盘内容 `!reflect.DeepEqual`，**立即写回磁盘**。
2. 写回内容包括：
   - **固化 `transport.chat_path`/`models_path`**（按 §3 规则推导的值）——若推导对某 provider 是错的（§3.2 最后两行），升级后第一次启动就把错误 URL 写死进配置；此后即使修复推导逻辑，**配置里的显式值仍然优先**；
   - `EnsureBuiltInProviders`：把 UseAI 内置 provider **强制置顶回填**（即使原配置刻意删除过它，只要没有同名条目就会被重新插入）；
   - 模型旧字段 `provider` → `provider_id` 迁移；`defense.enabled` 默认开启。
3. 启动/热加载日志会出现"配置已自动升级并写回磁盘"（`cmd/server/main.go`，本窗口新增）。
4. 叠加 `dccfefd`（v0.2.72）：Web 管理页探测成功后把探测推导的 transport 随保存写入配置——同一固化效应的第二入口。

**定位意义**：如果升级后某 provider 从"能用"变"上游 404"，且 config.json 里新出现了 `transport` 字段——即为本发现与发现 #2 的叠加，属于本窗口改动的直接后果。

## 7. 现场定位指引（在部署机上按序执行）

1. **确认故障模型绑定的 provider 类型**：管理页日志该请求的 `provider` 字段，或直接看 config.json 中对应 provider 的 `type`。若为 `anthropic` → 命中发现 #1。
2. **看 config.json 是否出现 `transport` 字段**（Windows：`%AppData%\vs-ai-proxy\config.json`；macOS/Linux：`~/.config/vs-ai-proxy/config.json`），以及启动日志是否有"配置已自动升级并写回磁盘"。若有 → 发现 #3 已发生，逐个核对 `chat_path` 与 §3.2 预期。
3. **复现发现 #1**（anthropic provider 场景）：
   - 管理页测试该 provider（`stream=false`）→ 预期成功；
   - `curl http://127.0.0.1:12345/v1/chat/completions -H 'Content-Type: application/json' -d '{"model":"<该模型>","stream":true,"messages":[{"role":"user","content":"hi"}]}'` → 预期 502（诊断 JSON 里 `upstream 4xx` 或 `upstream_server_error`），或响应体出现 `event: message_start` 等 Anthropic SSE 泄漏。
4. **复现发现 #2**（若存在非版本路径 base_url）：对同一 provider 发流式请求，看上游 404；对比 `config.json` 中该 provider 升级前后 base_url + chat_path 的拼接结果。

## 8. 修复方向评估（**仅供参考，未动任何代码，需批准后实施**）

1. **anthropic 流式修复（必须）**：工作区已有的未提交修复（`SendAnthropicChatStreamRequest` 聚合 Anthropic SSE → 复用非流式转换 → `writeOpenAIChatResponseAsSSE` 统一写出）方向正确，与非流式同一语义。需在批准时确认两个设计权衡：
   - 当前实现是**全量聚合后再一次性写出**：VS 端会"长时间无输出 → 一次性吐完"，长回复体验差、且大响应受内存约束；后续可演进为增量转换（content_block_delta → delta chunk），但那是优化项而非 correctness 项；
   - 终态判定依赖 `message_stop` 事件而非 EOF/换行，测试已覆盖"无换行符结尾 + 连接不关闭"的网关行为，这套用例应随修复一并提交。
2. **transport 固化的纠偏（视现场确认结果）**：若现场确认存在被写错的 `chat_path`，可选：(a) 文档指引用户显式改 config.json 的 `transport.chat_path` 或调整 base_url；(b) 代码层提供一次性迁移修正。二者都等现场数据再定。
3. **删除 debug println**（发现 #4）：一行删除，随下次发版。
4. **发版前补一个发布门槛**：把"VS 固定 stream=true"写进发布准入清单（docs/26 已有先例），任何新 provider 类型必须同时过流式用例——本次正是测试页（非流式）覆盖不到流式分支造成的漏网。
