## 1. 总结结论

API-Switch 最值得借鉴的不是 UI，而是三类产品能力：

1. **多协议、多 endpoint 探测**：用户输入一个 base_url 后，系统会同时尝试不同协议、不同 URL 形态，并给出 `detected_type`、`corrected_base_url`、`available_types`。这能显著减少用户配置错误。
2. **模型池与排序策略**：API-Switch 将“上游渠道 channel”和“对外模型 entry”拆开，支持 group、alias、fuzzy match、AUTO fallback、自定义排序、最快优先、最新优先、score 排序基础。
3. **模型元数据目录**：`models.json` 已包含 220 个模型，且每个模型都有 `limit.context` 和 `limit.output`。这说明“自动填充上下文长度、最大输出 token、tools/vision/reasoning 能力”是可落地的。

对 `vs-ai-proxy` 来说，最优路线不是整体照搬 API-Switch，而是选择性吸收：

- **P0**：在 Web 新增/编辑模型时，按模型名自动补齐 `context_length`、`max_output_tokens`、能力字段，并允许用户覆盖。
- **P0**：新增 provider/base_url 探测接口，自动识别 OpenAI-compatible / Ollama / Anthropic / Gemini / Azure 等候选能力，至少先覆盖 OpenAI-compatible 与 Ollama。
- **P1**：把 provider priority 扩展为更可运营的候选排序：自定义优先级 + 最近成功率 + 延迟 + 冷却状态。
- **P1**：引入更完整的模型元数据目录，但必须转换成当前 Go 项目的 `ModelProfile` 格式，不能把 API-Switch 的前端 TypeScript catalog 直接塞进运行时。

## 2. API-Switch 已实现的关键优点

### 2.1 Endpoint 探测与纠错

API-Switch 的 `channel_service.rs` 中存在明确的探测链路：

- `probe_url()` 会在有 `api_type + api_key` 时调用 `detect_endpoint_and_collect()`，返回 `detected_type`、`corrected_base_url`、`available_types`。
- 如果没有完整凭据，则退化为 `HEAD` / `GET` 基础连通性探测。
- `fetch_models()` 会先执行 `detect_endpoint_guess()`，再使用修正后的类型和 base_url 拉取模型。

证据位置：

- `src-tauri/src/services/channel_service.rs:318-432`
- `src-tauri/src/services/channel_service.rs:468-520`

设计价值：

- 用户经常把 `https://xxx/v1/chat/completions`、`https://xxx/v1`、`https://xxx` 混用。API-Switch 会尝试修正，而不是让用户靠报错猜。
- 探测结果区分 `Usable` 和 `Reachable`。前者表示可拉到模型，后者表示 endpoint 能响应但模型列表不可用或鉴权/格式有问题。
- 返回结构化错误码，如 `ERROR_CODE_INVALID_CREDENTIALS`、`ERROR_CODE_TIMEOUT`、`ERROR_CODE_ENDPOINT_UNREACHABLE`，利于 Web 端提示。

对 `vs-ai-proxy` 的启发：

- 当前我们已有 Web 测试连接和测试聊天，但更偏“单 provider 单协议测试”，缺少“URL/协议自动探测与纠错”。
- 应新增 `/admin/api/providers/probe` 或 `/admin/api/provider/probe`，输入 `base_url/api_key/type`，输出：

```json
{
  "reachable": true,
  "detected_type": "openai",
  "corrected_base_url": "https://api.example.com/v1",
  "available_types": ["openai"],
  "models_count": 42,
  "warnings": [],
  "errors": []
}
```

### 2.2 多协议候选探测

API-Switch 的探测不是只试用户选中的协议。`endpoint_probe_api_types()` 会先放入用户选择的类型，再追加 `openai`、`responses`、`anthropic`、`gemini`、`azure`。

证据位置：

- `src-tauri/src/services/channel_service.rs:759-768`

同时，`detect_endpoint_candidates()` 会对 `UserUrl` 和 `BaseSite` 两个 scope 并发探测。

证据位置：

- `src-tauri/src/services/channel_service.rs:709-756`

设计价值：

- 用户选择错 API 类型时，系统仍能提示“这个 endpoint 更像 Anthropic/Gemini/OpenAI”。
- 对 SaaS 聚合商和代理服务很有价值，因为它们常同时支持多个协议。

对 `vs-ai-proxy` 的建议：

- 第一阶段不要一次性做五协议全量转换，否则会扩大测试面。
- 建议按以下顺序落地：
  1. OpenAI-compatible：`/models`、`/v1/models`、`/api/models`、`/api/v1/models`。
  2. Ollama：`/api/tags`、`/api/show`。
  3. Anthropic：`/v1/models`，后续再做消息协议转换。
  4. Gemini/Azure：作为 P1，不阻塞 Visual Studio Copilot 主目标。

### 2.3 base_url 变体枚举

API-Switch 对 OpenAI 类型会尝试多个模型列表 URL：

- adapter 默认 URL
- `/models`
- `/v1/models`
- `/api/models`
- `/api/v1/models`
- `/v2/models`

证据位置：

- `src-tauri/src/services/channel_service.rs:647-684`
- `src-tauri/src/services/channel_service.rs:1134-1164`

设计价值：

- 大量第三方 OpenAI-compatible provider 的 base_url 规范不一致。
- 这个策略比要求用户填写绝对正确的 URL 更符合产品化要求。

对 `vs-ai-proxy` 的建议：

- provider 保存前可以不强制自动修正，但 Web 应提示建议修正：
  - 用户填写 `https://host`，探测成功 URL 是 `https://host/v1/models`，则建议保存 `https://host/v1`。
  - 用户填写 `https://host/v1/chat/completions`，应建议保存 `https://host/v1`。
- 修正必须由用户确认或以“应用建议”按钮触发，避免误改企业内网网关 URL。

### 2.4 模型池 entry 与 channel 拆分

API-Switch 数据结构中：

- `channels` 表示上游渠道，包含 `api_type/base_url/api_key/available_models/selected_models/enabled/response_ms`。
- `api_entries` 表示可路由模型条目，包含 `channel_id/model/display_name/sort_index/enabled/cooldown_until/response_ms/provider_logo/release_date/model_meta/score/group_name`。

证据位置：

- `src-tauri/src/database/schema.rs:6-39`
- `src-tauri/src/database/schema.rs:226-236`

设计价值：

- 一个 provider/channel 可以有多个模型。
- 同一个模型可以绑定多个 channel，形成候选列表。
- `api_entries` 能保存测速、分组、展示名、冷却状态，不污染 provider 基础配置。

对 `vs-ai-proxy` 的现状对比：

- 当前 `ProviderConfig` 与 `ModelConfig` 已经初步拆分。
- `ModelConfig.ProviderID` 可以绑定 provider，空值代表自动路由。
- 但我们没有单独的 `entry` 层，模型的测速、成功率、冷却、排序还没有稳定落点。

建议：

- 不建议马上引入 SQLite 或完整 `api_entries` 表，这会明显增加复杂度。
- 建议先在 `config.json` 的 `models[]` 上补轻量字段：

```json
{
  "name": "z-ai/glm-5.2",
  "provider_id": "usecpa",
  "enabled": true,
  "priority": 10,
  "group": "auto",
  "context_length": 1000000,
  "max_output_tokens": 131072
}
```

- 运行态指标如失败次数、冷却到期时间、延迟分布应先放内存 store，不直接写入配置文件。配置文件只保存用户意图，不保存高频运行态。

### 2.5 路由解析顺序

API-Switch 的 `resolve()` 路由规则：

1. 空模型归一化为 `auto`。
2. group 精确匹配。
3. model 精确匹配。
4. display_name 精确匹配。
5. model fuzzy contains 匹配。
6. fallback 到 `auto` group。

证据位置：

- `src-tauri/src/proxy/router.rs:99-184`

设计价值：

- 支持“对外暴露稳定模型名”，背后切换多个上游。
- 支持用户不关心模型时使用 `auto`。
- 支持 alias/display_name。

对 `vs-ai-proxy` 的建议：

- Visual Studio Copilot 场景中，模型身份必须稳定、可解释，不能过度依赖 fuzzy。
- 推荐路由顺序：
  1. `model@provider_id` 精确匹配。
  2. 完整上游模型名精确匹配。
  3. Visual Studio 展示名还原。
  4. 唯一 basename 匹配。
  5. `group` / `auto` fallback。
  6. 如果 basename 不唯一，拒绝并返回结构化错误，不做 fuzzy 猜测。

这和我们最近修复 Visual Studio `glm-5.2`、`:latest`、display_name 回传问题的方向一致。

### 2.6 排序模式与模型权重

API-Switch 支持三种排序：

- `custom`：按 `sort_index`。
- `fastest`：按 `response_ms`。
- `latest`：按 `release_date`。

证据位置：

- `src-tauri/src/proxy/router.rs:7-60`
- `src-tauri/src/proxy/router.rs:186-191`

API-Switch 还在 `pool_service.rs` 中定义了 score：

- 模型能力分 60%
- channel 速度 20%
- entry 对话速度 20%

证据位置：

- `src-tauri/src/services/pool_service.rs:27-44`

设计价值：

- “优先级”不再只是用户手工排序，还能结合实测速度和模型能力。
- 对多 provider 同模型非常有用。

对 `vs-ai-proxy` 的建议：

- 不建议 P0 直接引入复杂 score，因为 Visual Studio Copilot 的核心诉求首先是稳定。
- P1 可以引入候选排序公式：

```text
candidate_score =
  manual_priority_weight
  + health_success_rate_weight
  + latency_weight
  + model_capability_weight
  - recent_error_penalty
```

建议默认排序仍以 `provider.priority` 为第一约束，避免用户无法理解为什么路由到某个 provider。

## 4. 关于“上下文大小等参数能否自动默认设置”

结论：**可以，而且应该做。**

当前 `vs-ai-proxy` 已经有基础能力：

- `ModelConfig` 有 `ContextLength`、`MaxOutputTokens`、`SupportsTools`、`SupportsVision`、`ReasoningEffort` 等字段。
- `/api/tags` 和 `/api/show` 会读取 `config.json` 模型配置和 `ModelCatalog.Profile()`。
- 默认兜底是 `context_length = 128000`、`max_output_tokens = 4096`。

证据位置：

- `internal/config/config.go:35-51`
- `internal/proxy/ollama_show.go:13-24`
- `internal/proxy/model_endpoints.go:104-169`
- `internal/provider/model_catalog.go:15-30`

当前短板：

- Web 新增模型时仍默认 `8192/4096`，用户容易填错。
- 保存模型时没有自动按模型目录回填元数据。
- 当前 Go 内置 `model-selection/*.json` 已有一部分模型，但覆盖面不如 API-Switch `models.json`。
- API-Switch `models.json` 的字段结构和当前 Go `ModelProfile` 不完全一致，需要转换层。

推荐设计：

### 4.1 默认值来源优先级

保存模型或模型发现时，按以下顺序生成最终默认值：

1. 用户显式填写的 `config.json.models[]` 字段。
2. 项目内置模型元数据目录。
3. provider 返回的模型能力信息；如果 provider 只返回 id，则只用于 identity，不用于能力。
4. provider 类型默认值。
5. 全局安全兜底。

建议兜底：

| 场景 | context_length | max_output_tokens | 原因 |
|---|---:|---:|---|
| 已命中元数据目录 | 使用目录值 | 使用目录值 | 最准确 |
| 未命中，OpenAI-compatible 现代模型 | 128000 | 4096 | 保守兼容 |
| 未命中，名称含 `glm-5` / `deepseek-v4` / `qwen3` 等长上下文关键词 | 262144 或 1000000，但标记为 inferred | 避免过小，但要提示推断 |
| 未命中，Ollama 本地模型 | 128000 | 4096 | 保守默认 |
| 用户明确覆盖 | 用户值 | 用户值 | 尊重用户 |

### 4.2 Web 端交互

新增/编辑模型时：

- 用户输入模型名后，前端调用后端 `/admin/api/models/metadata?name=...&provider_id=...`。
- 如果命中元数据，自动填充：
  - `context_length`
  - `max_output_tokens`
  - `supports_tools`
  - `supports_vision`
  - `reasoning`
  - `family`
- UI 显示来源：
  - `来自内置模型目录`
  - `来自 provider 探测`
  - `系统推断，建议确认`
  - `用户覆盖`

不要让用户面对空白数字输入框。

### 4.3 后端保存路径

后端 `saveModels` 和 `saveConfig` 应在校验后做一次 `enrichModelDefaults()`：

```go
func enrichModelDefaults(models []config.ModelConfig, catalog provider.ModelMetadataCatalog) []config.ModelConfig
```

规则：

- 用户已有正数值，不覆盖。
- 目录命中时补空值。
- 未命中时填全局保守默认。
- 补齐结果写回 `config.json`，这样 Web 下次打开能看到最终值。

这比只在 `/api/tags` 动态补齐更好，因为用户可见、可改、可排查。

## 5. 哪些能力不建议照搬

### 5.1 不建议照搬 fuzzy contains 路由

API-Switch 的 fuzzy contains 对个人 API 网关体验友好，但对 Visual Studio Copilot 风险较高：

- VS 可能回传短名、展示名、`:latest`、甚至 provider display prefix。
- fuzzy 在多 provider 同 basename 时可能误路由。
- 我们已经遇到过 `glm-5.2` 与上游真实模型名不一致的问题。

建议：

- fuzzy 只能用于 Web 搜索，不用于真实请求路由。
- 真实请求路由必须可解释：精确、唯一、否则报错。

### 5.2 不建议 P0 引入 SQLite entry 表

API-Switch 的 `channels/api_entries/usage_logs/config` 表适合完整个人 API 网关，但 `vs-ai-proxy` 当前定位是 Visual Studio Copilot provider 扩展代理，配置文件单一事实来源更符合低安装成本。

建议：

- P0/P1 继续使用 `config.json`。
- 运行态健康指标放内存 store。
- 如果未来要做长期统计和策略学习，再考虑 SQLite。

### 5.3 不建议直接复用 API-Switch 的 `models.json` 原格式

原因：

- API-Switch 字段是前端 catalog 友好的格式。
- 当前 Go 项目运行时使用 `ModelProfile`。
- 直接读两套格式会让配置理解成本升高。

建议：

- 写一个转换脚本或转换函数，把 API-Switch `models.json` 转换为当前项目的 `internal/provider/model-selection/*.json` 或新的 `internal/provider/model-metadata.json`。
- 转换后格式必须统一。

## 6. 建议落地路线

### P0：模型元数据自动补齐

目标：

- 用户只填模型名和 provider，就能得到合理的 `context_length/max_output_tokens`。
- Web 不再让用户凭感觉填写上下文大小。

建议任务：

1. 增加 Go 侧通用 `ModelMetadataCatalog`，支持按以下 key 查找：
   - 完整模型名：`zhipuai/glm-5.2`
   - 去 namespace：`glm-5.2`
   - provider alias：`z-ai -> zhipuai`
   - 去 suffix：`:latest`、`-preview`、`-free` 等只用于匹配，不改变真实模型名。
2. 从 API-Switch `models.json` 转换一份内置元数据。
3. `saveModels` 保存时自动补齐缺失字段。
4. Web 模型表展示“元数据来源”和“是否用户覆盖”。
5. 为 `glm-5.2`、`z-ai/glm-5.2`、`deepseek-v4-flash`、`gpt-4.1`、未知模型写单元测试。

### P0：provider URL 探测与纠错

目标：

- 用户填错 base_url 时，Web 直接给出修正建议。

建议任务：

1. 新增 `/admin/api/providers/probe`。
2. 第一阶段支持：
   - OpenAI-compatible：多 URL 变体 `/models`、`/v1/models`、`/api/models`、`/api/v1/models`。
   - Ollama：`/api/tags`。
3. 返回结构化诊断：
   - 网络不可达
   - 认证失败
   - 模型列表为空
   - 协议疑似不匹配
   - 建议 base_url
4. Web provider 编辑页增加“探测并修正”按钮。

### P1：候选排序增强

目标：

- 不只按 provider priority，而是结合运行健康度。

建议策略：

- provider priority 仍是第一层，保证用户可控。
- 同 priority 内按：
  - 最近成功率高优先。
  - 平均延迟低优先。
  - 正在冷却的跳过。
  - 连续失败触发短期熔断。

这比直接照搬 API-Switch 的 score 更稳。

### P1：模型分组与 auto

目标：

- 让 Visual Studio 用户可以只选 `auto` 或 `coding`，背后由代理选择最合适候选。

建议：

```json
{
  "name": "z-ai/glm-5.2",
  "provider_id": "usecpa",
  "group": "coding",
  "priority": 10,
  "enabled": true
}
```

路由：

- `coding` 命中 group。
- `auto` 命中 auto group。
- group 内按 priority/health 排序。

### P2：长期运行健康模型

目标：

- 支持 7*24 小时运行。

建议：

- 内存级 circuit breaker。
- 错误分类：
  - 401/403：配置/API key 问题，禁用或强提醒。
  - 429/503：短冷却，不禁用。
  - connect timeout：网络问题，短冷却。
  - provider 返回模型不存在：模型配置问题。
- Web 日志中展示“失败类型”和“建议动作”。

## 7. 对当前项目核心目标的影响

当前核心目标是：

> 让 Visual Studio Copilot 支持更多非内置大模型提供商，而不是做一个通用 API 网关。

因此取舍应明确：

- 应吸收 API-Switch 的 provider 探测、模型元数据、排序思路。
- 不应把 API-Switch 的完整多协议 API 网关形态一次性搬过来。
- Visual Studio Copilot 的特殊点是模型发现、模型展示名、流式响应兼容、finish_reason、`:latest`、display_name 回传。所有新增策略必须优先保护这些路径。

## 8. 推荐的最小闭环设计

建议下一步形成这个闭环：

```text
Web 新增 provider
  -> 探测 base_url / api_type / models
  -> 用户确认 corrected_base_url
  -> 保存 provider
  -> 拉取 models
  -> 用模型元数据目录补齐 context/output/tools/vision/reasoning
  -> 保存 config.json
  -> 热更新 registry/catalog
  -> /api/tags 给 Visual Studio 暴露稳定模型
  -> VS 请求进入可解释路由
  -> 日志记录 provider/model/upstream/错误类型/建议动作
```

这个闭环能同时解决：

- 用户不会填错 base_url。
- 用户不会乱填 context length。
- Visual Studio 看到的模型能力更准确。
- 多 provider 同模型能排序、故障转移。
- 出错时能知道是配置、网络、provider、模型名还是程序兼容问题。

## 9. 最终建议

优先级排序：

1. **先做模型元数据自动补齐**：低风险、高收益，直接改善 Web 配置体验和 VS 模型能力展示。
2. **再做 provider URL 探测与纠错**：减少用户配置错误，是上线后支持成本最低的投资。
3. **然后做候选健康排序与短冷却**：提升 7*24 稳定性。
4. **最后考虑 group/auto 与更复杂 score**：这是增强能力，不是当前最紧急问题。

不建议：

- 不建议 P0 引入 SQLite。
- 不建议真实路由使用 fuzzy contains。
- 不建议让用户继续手填上下文大小作为主要路径。
- 不建议同时保留多套模型元数据格式。

一句话结论：

> API-Switch 的最佳借鉴点，是把“用户手动配置”升级为“系统探测 + 元数据补齐 + 可解释排序”。`vs-ai-proxy` 应围绕 Visual Studio Copilot 的模型发现与稳定路由做轻量吸收，而不是整体复制 API-Switch 的通用网关架构。

### 10.2 已落地：轻量 provider 健康排序与短冷却

已实现 P1 中低成本、高价值的候选健康排序：

- provider priority 仍是第一约束，保证用户可解释、可控制。
- 同 priority 内按运行态健康排序：
  - 连续失败少的优先。
  - 成功率高的优先。
  - 平均延迟低的优先。
- provider 出现 429、503、timeout、401、403 等错误后进入短冷却。
- 有其他可用 provider 时跳过冷却中的 provider。
- 如果所有候选都在冷却，仍返回候选作为最后兜底，避免直接无路由。
- 运行态健康指标只保存在内存，不写入 `config.json`。

这符合本文前面的取舍：先提高 Visual Studio Copilot 多 provider 故障转移稳定性，不引入 SQLite，不照搬 API-Switch 的完整 score/channel 架构。
