# UseAI 大请求间歇性 502 诊断与重试边界复盘

日期：2026-07-22

## 背景

真实 VS/Copilot 工具调用请求在 UseAI `deepseek-v4-flash` 上间歇性出现：

```text
POST /v1/chat/completions - 502
error_code=network_error
reason="无法连接上游"
request_bytes="400.5 KB"
upstream_bytes="403.7 KB"
```

早期日志只能看到“无法连接上游”和粗粒度 `stream_state=upstream_connecting`，容易误判为 DNS/TCP 连接失败，也无法确认代理是否重复提交了同一大请求。

## 根因判断

本次通过 `httptrace` 把 provider 内部每次真实 HTTP 尝试拆成阶段：

- `preparing_request`
- `resolving_dns`
- `connecting`
- `tls_handshake`
- `writing_request`
- `waiting_response_headers`
- `receiving_response_headers`

复测时，失败样本从旧的 `network_error` 收敛为：

```text
error_code=upstream_no_response
stream_state=upstream_waiting_response_headers
attempts_summary="useai/deepseek-v4-flash ... (upstream_attempts=1 last=waiting_response_headers/upstream_no_response)"
```

这个阶段说明代理已经把请求写给上游，并正在等待响应头。结合 `request_bytes` 与 `upstream_bytes` 差值很小，可以排除“代理把 400KB 请求异常膨胀成大得多的请求”这一类问题；更符合 UseAI/new-api/sub2api 渠道排队、网关关闭连接、上游首响应失败或中间 CDN/WAF 断开的现象。

## 行业边界

这次修复按两个外部标准收敛：

- RFC 9110 对非幂等方法的要求：代理不能自动重试非幂等请求，除非能确认请求没有被应用，或请求语义实际是幂等。
- Go `net/http.Transport` 的行为：标准库只在受限条件下对网络错误重试；本项目不再人为设置 `Idempotency-Key`，避免把 chat POST 标成可透明重放。

因此本项目采用的边界是：

- 代理自己只在 `preparing_request`、`resolving_dns`、`connecting`、`tls_handshake` 阶段允许短重试。
- 一旦进入 `writing_request` 或 `waiting_response_headers`，代理不再手动重放 chat POST。
- 陈旧空闲连接等标准库能确认安全的场景，交给 Go Transport 内部处理；代理层不再额外打 replay 标记。
- 结构化传输失败不会触发流式/非流式备用模式，避免同一大 POST 因 fallback 再提交一次。
- HTTP 5xx 的历史短重试仍保留在 `DefenseEnabled` 下，用于 new-api/sub2api 直接透出 503 的场景；它不是零二次请求模式，发布说明和排障时必须明确这一点。

## 本次对策

1. provider 层新增 `UpstreamAttempt`，错误链携带每次上游 HTTP 尝试的阶段、耗时、HTTP 状态码和脱敏错误文本。
2. proxy 层把 `waiting_response_headers` / `receiving_response_headers` 的网络断开归类为 `upstream_no_response`。
3. 新增 `upstream_stream_interrupted`，用于区分“上游流已经开始但中途断开”和“代理协议解析失败”。
4. `X-Proxy-Attempts-Summary` 增加 `upstream_attempts=N last=<stage>/<category>`。
5. `X-Proxy-Stream-State`、store 日志、响应头统一通过 `setProxyDiagnosticHeader` 更新，避免响应头和持久化日志不一致。
6. `large_request_matrix_diagnostic.sh` 支持 `REPEAT`、direct/proxy/proxy-only 模式和聚合成功率，便于短冒烟、30 轮 soak 和整夜稳定性测试。

## 已验证现象

2026-07-23 真实上游复测结论：

- `REPEAT=10`、UseAI 400KB、`MODE=proxy-only`：7/10 成功，3/10 失败。
- 3 次失败全部为 `upstream_stream_interrupted`，`stream_state=upstream_connected`，说明已经连上上游但 SSE 流中途断开，不再虚报为“无法连接上游”。
- 10 轮中 `request_bytes=400000`、`upstream_bytes=400000`、`delta_bytes=0`，未观察到代理请求体异常放大。
- `REPEAT=3`、UseAI/DeepSeek 400KB、`MODE=direct-proxy`：UseAI proxy 3/3 成功，但 direct 有 2/3 curl 层失败；DeepSeek 官方 direct 3/3 返回 `402`，proxy 3/3 稳定映射为 `upstream_api_error` 且 `last=http_402/upstream_api_error`。
- 上述结果说明代理诊断已经能区分“上游流中断”“上游账号/API 拒绝”和旧的笼统网络错误；但 UseAI 真实上游链路仍存在间歇性失败，不能承诺完全消除。

## 剩余风险

- 代理不能保证 UseAI/new-api/sub2api 上游通道不再间歇性失败；它只能准确暴露失败阶段，并避免在危险阶段自行重放。
- `DefenseEnabled=true` 下仍保留 HTTP 5xx 短重试和 5xx 模式兜底，这是为了可用性，不是严格零重试模式。
- `.bin/useai-large-diagnostic/` 和 `.bin/large-request-matrix/` 是本地诊断产物，权限按 0600/0700 处理，不应提交到版本库。
