## 2. 工具协议背景（设计事实）

### 2.1 声明 → 上游 → 归一 → VS 执行

```text
VS 声明 tools[]
    → proxy 转发上游（透传 / 必要方言）
    → 上游返回 tool_calls
    → proxy 别名归一 / 参数边界校验
    → VS 按已声明 schema 执行
```

### 2.2 git 的参数形态

正确 git 工具参数形态是 **`args[]` 字符串数组**（不含前导 `git`）：

```json
{
  "name": "git",
  "arguments": "{\"args\":[\"status\",\"--short\"]}"
}
```

shell 类工具（`run_in_terminal` / `powershell` / `terminal`）使用 **`command` 字符串**，与 git schema **不兼容**。

### 2.3 当前别名目录（代码事实，非本轮修改）

`internal/proxy/copilot_tools.go` 中 git 族：

```text
Canonical: git
Aliases:
  git_command → git, powershell, terminal, run_in_terminal
  git_status  → git, powershell, terminal, run_in_terminal
  git_diff    → git, powershell, terminal, run_in_terminal
  git_log     → git, powershell, terminal, run_in_terminal
```

设计原则（同文件注释）：

1. 只映射到**当前请求已声明**的目标工具，不凭空发明工具。
2. 文件语义工具**不得**降级到 shell（避免 schema 不匹配）。
3. git 别名目前仍带 shell 降级路径 → **次要设计债**（见第 5 节）。

## 3. 实测矩阵（2026-07-22）

以下均使用真实 `xiaomimimo` Key；摘要只记录结论字段，不含密钥。

### 3.1 Happy path：git 链路可用

| # | 路径 | 场景 | finish | tools | 参数 |
| ---: | --- | --- | --- | --- | --- |
| A | proxy | 强制 `git`，无 client budget | `tool_calls` | `git` | `{"args":["status","--short"]}` |
| B | proxy | `auto`，仅声明 git | `tool_calls` | `git` | 同上 |
| C | proxy | 强制 `git` + `max_tokens=64` | `tool_calls` | `git` | 同上（本次 reasoning ≈ 11 tokens） |
| D | proxy | 流式强制 `git` | `tool_calls` | `git` | 分片拼成完整 args |
| E | 直连 | 强制 `git` + `max_completion_tokens=128` | `tool_calls` | `git` | 同上 |
| F | 直连 | 强制 `git` + `max_completion_tokens=64` | `tool_calls` | `git` | 同上 |
| G | proxy | VS 工具集内强制 `git` | `tool_calls` | `git` | 同上 |

Proxy 响应头样例：

```text
X-Proxy-Provider: xiaomimimo
X-Proxy-Request-Tools: declared: git
X-Proxy-Response-Tools: returned: git
X-Proxy-Upstream-Model: mimo-v2.5
```

**结论：API Key、上游可达性、MiMo 输出 token 方言、proxy 对 git 参数透传，在正常预算下均正常。**

### 3.2 主失败模式：reasoning 吃光 completion budget

提示词刻意要求「先详细长推理，再调用 git」时，直连结果：

| max_completion_tokens | finish_reason | tool_calls | 现象 |
| ---: | --- | ---: | --- |
| 32 | `length` | 0 | reasoning 烧满，无工具 |
| 48 | `length` | 0 | 同上 |
| 96 | `length` | 0 | reasoning_tokens ≈ 95，仍无工具 |
| 64（长推理提示） | `length` | 0 | content 空；reasoning 截断 |

特征：

- HTTP **200**（不是 4xx/5xx）
- `finish_reason=length`
- `tool_calls` 为空
- `usage.completion_tokens_details.reasoning_tokens` 接近或等于 budget
- 客户端侧表现：**「模型没调工具 / 工具调用失败」**

历史排查中还观察到：极紧预算下偶发 content 中出现截断的类 XML 伪工具文本（如 `<tool_call>...`），同样**不会**变成可执行 `tool_calls`。本轮「长推理」场景更多表现为纯 reasoning 烧尽。

**这与 doc 33 的机制同源**：MiMo 默认输出 `reasoning_content`，推理 token 计入 completion budget。doc 33 解决的是「字段名用错（`max_tokens` vs `max_completion_tokens`）」；本轮暴露的是「字段名正确后，**预算绝对值仍可能不够 reasoning + tool_calls**」。

### 3.3 VS 多工具目录：模型选型偏好，非 schema 崩坏

| 场景 | 结果 |
| --- | --- |
| 同时声明 `git / git_status / run_in_terminal / read_file / ...`，`tool_choice=auto` | 模型本次返回 `run_in_terminal` + `{"command":"pwd"}` |
| 强制 `tool_choice=git`（同一工具集） | 正确返回 `git` + `args[]` |
| 仅声明 `git` + `git_status`，`auto` | 模型返回 `git_status`（已声明名，proxy 不改写） |
| 强制 `git_status` | 返回 `git_status`，args 可为 `{}` 或 `{"repoPath":"."}` |

说明：

1. **Proxy 没有把 git 偷偷改成 shell**；auto 下选 shell 是模型行为。
2. 当 `git_status` **已在请求中声明**时，它是合法工具名，不是「未声明别名」。
3. 别名归一只在「模型吐出未声明别名 → 映射到已声明目标」时介入。

### 3.4 多轮 tool result

| 场景 | 结果 |
| --- | --- |
| 回传 tool result，保留 `reasoning_content` | HTTP 200，可继续调用工具或 stop |
| 回传 tool result，不带 `reasoning_content` | HTTP 200（与 Kimi 严格空历史不同，见 doc 33） |

### 3.5 本地日志侧（补充）

本轮历史 `logs.json` 中 **无 MiMo + git 失败的直接命中**；既有失败多为无关 404 / 其它 provider 鉴权。  
**不能**用「日志没有 git 失败」否定用户现场；只能说明默认日志粒度不足以捕获「200 + length + 无 tools」类语义失败。

## 5. 根因说明

### 5.1 主要可复现失败模式（用户可感知的「git 工具失败」）

对 **reasoning 模型 + 工具调用**（MiMo 是典型）：

```text
completion budget
  = reasoning_tokens + tool_call 结构 tokens + 可见 content tokens
```

当客户端（或某条路径）给出偏小的 `max_tokens` / `max_completion_tokens`，且模型先产生较长 `reasoning_content` 时：

1. 预算在 reasoning 阶段耗尽；
2. `finish_reason=length`；
3. **没有**结构化 `tool_calls`；
4. VS/客户端看到「没调用工具」或「工具失败」；
5. 代理若仍返回 HTTP 200，诊断层容易漏报（不像 4xx 那样显眼）。

这是一条有 live 证据支撑的失败路径，但不能据此断言它覆盖所有 MiMo/git 失败现场。后续仍应以同一 `request_id` 下的真实请求字段、`finish_reason`、`usage` 和工具诊断头为准。

与 doc 33 的关系：

| 文档 | 问题层 | 表现 |
| --- | --- | --- |
| 33 | **字段方言** | 写 `max_tokens` 时预算语义错误，小预算几乎全耗在 reasoning |
| **37（本文）** | **预算绝对值** | 字段正确后，budget 仍可能不够「推理 + 工具调用」 |

### 5.2 次因：多工具 auto 选型

在 VS 同时提供 `git` 与 `run_in_terminal` 时，模型可能选 shell。  
这**不是**协议错误；若用户期望「必须走 git 工具」，属于产品/提示/tool_choice 策略问题，不是 proxy 把 schema 弄坏。

### 5.3 次要设计债：git 别名 → shell

当且仅当：

1. 模型输出未声明别名（如 `git_status`），且  
2. 请求里**没有** `git`，但有 `run_in_terminal` 等 shell，  

别名解析可能落到 shell，而参数仍是 git 形态（`args[]`），导致「工具名变了、参数对不上」。  
文件工具族已明确禁止此类降级；git 族尚未完全对齐该原则。  
**本轮 live 主因不是它**，但属于值得单独修的全局一致性项。

## 7. 对策（设计级，待确认后再实现）

按优先级排列。实现前需用户确认；本文只定义方向与验收标准。

### 7.1 【P0 / 待进一步标定】Provider 级最小安全 completion budget

**目标**：对「工具调用 + reasoning」类 provider（至少 `xiaomimimo`），当客户端 budget 过小且请求携带 `tools` 时，抬到安全下限，而不是 per-tool 特判。

**建议归属层**：`internal/provider/capabilities`（与 `OutputTokenParam` 同层），禁止散落在 chat handler 的 model 名分支。

**方向性参数（实现时再标定）**：

- 触发条件：请求含 `tools` / 强制 tool_choice，且 client budget < 安全下限。  
- 下限候选：例如 512 或 1024（需用 MiMo 再扫一轮 reasoning 峰值后定）。  
- 仅抬升、不压低客户端更大 budget。  
- 响应头可标注 `X-Proxy-Budget-Adjusted: ...` 便于观测。

**验收**：

1. 直连/代理在 mct=32–96 + 长推理提示下，调整后稳定出现结构化 `tool_calls` 或明确拒绝/诊断（不得静默 length 空工具）。  
2. 无 tools 的纯聊天行为不被误伤（或有独立策略）。  
3. 单元/集成测试覆盖 capability，不写死 `mimo-v2.5` 字符串在 handler。

### 7.2 【P1 / 已补强】语义失败可观测性

对 `finish_reason=length` 且 `tool_calls` 为空 的响应：

- 日志：`request_id`、`provider`、`model`、`completion_tokens`、`reasoning_tokens`、client/upstream budget。  
- 日志：`tool_outcome=truncated_no_tools`。  
- 响应头：OpenAI 非流式与 VS/OpenAI SSE 兼容路径可见 `X-Proxy-Tool-Outcome: truncated_no_tools`；已开始边写正文的 passthrough 流路径不能保证客户端还能收到新增响应头，但日志字段仍会记录。  
- 避免只显示「200 OK」导致 VS 侧无法区分成功与「预算截断」。

**验收**：复现 3.2 时，日志/诊断一眼可判定为 budget 截断，而非「上游无响应」。

### 7.3 【P2】git 别名去掉 shell 降级

将：

```text
git_status / git_diff / git_log / git_command → git, powershell, ...
```

收敛为：

```text
→ 仅 git（及同请求已声明的 git 族目标）
```

与文件工具「不降级 shell」原则对齐。  
**不做**参数形态强行互转（`args[]` ↔ `command`），除非有统一的 tool argument shape 层且覆盖全族。

**验收**：

1. 仅声明 shell 时，未声明的 `git_status` **不**被改写成 shell。  
2. 同时声明 `git` 时，别名映射到 `git`。  
3. 现有 `tool_aliases_test` / e2e 更新并全绿。

### 7.4 【P3 / 可选】截断伪工具文本

若再次稳定复现 content 中的 `<tool_call>...` 截断文本：

- 优先仍是抬 budget（7.1），而不是正则「抢救」半截 XML。  
- 若要做 content→tool_calls 抢救，必须：仅在明确方言、完整闭合、且名字落在已声明 tools 时启用；禁止半截发明。

### 7.5 明确延后

| 项 | 原因 |
| --- | --- |
| stash experimental git shape 归一 | 无 happy path 证据 |
| 强制 auto 时改写 shell→git | 违背「不伪造工具」 |
| 仅文档不修观测 | 会重复「看起来 200 实际失败」的排障成本 |

## 8. 复现与对照手册（不改代码时可用）

### 8.1 验证 happy path（应成功）

```bash
# 经本地代理，强制 git
curl -s http://127.0.0.1:12345/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "mimo-v2.5",
    "messages": [{"role":"user","content":"Use git tool: status --short. No text."}],
    "tools": [{
      "type":"function",
      "function":{
        "name":"git",
        "description":"Run git",
        "parameters":{
          "type":"object",
          "properties":{"args":{"type":"array","items":{"type":"string"}}},
          "required":["args"]
        }
      }
    }],
    "tool_choice": {"type":"function","function":{"name":"git"}},
    "stream": false
  }'
```

期望：`finish_reason=tool_calls`，`function.name=git`，arguments 含 `args` 数组。

### 8.2 复现主失败（预算截断）

直连或代理，设置小 budget，并要求长推理：

```json
{
  "model": "mimo-v2.5",
  "max_completion_tokens": 64,
  "messages": [{
    "role": "user",
    "content": "请先完整、详细地逐步推理，再调用 git 工具执行 status --short。"
  }],
  "tools": [ /* git */ ],
  "tool_choice": "auto"
}
```

期望（当前上游行为）：`finish_reason=length`，`tool_calls` 空，`reasoning_tokens` ≈ budget。

### 8.3 对照检查清单

1. 看 `finish_reason` 是否为 `length`。  
2. 看 `usage.completion_tokens_details.reasoning_tokens`。  
3. 看 proxy 头 `X-Proxy-Response-Tools` 是否 `returned: ...`。  
4. 看 proxy 头 `X-Proxy-Tool-Outcome` 或日志 `tool_outcome` 是否为 `truncated_no_tools`。  
5. 用同一 `request_id` 聚合日志，勿把并发请求串读。  
6. 区分「模型选了 shell」与「预算截断无工具」。

## 10. 结论摘要

1. **MiMo git 工具在充足 budget 下经 proxy/直连均可稳定返回正确 `git` + `args[]`。**  
2. **用户可感知的主要可复现失败模式是：reasoning 耗尽 completion budget → `finish=length` → 无 `tool_calls`。**  
3. 这是 **reasoning 模型 + 工具调用** 的通用问题，应做 **provider capability 级 budget 与观测**，而不是 git 专用补丁。  
4. VS 多工具 auto 选 shell 是模型偏好；git→shell 别名是次要设计债。  
5. 已补强 `X-Proxy-Tool-Outcome: truncated_no_tools` 诊断，避免把「200 + length + 空工具」误看成普通成功。  
6. Provider 级最小 budget 仍需进一步标定，不应作为已验证实现结论。
