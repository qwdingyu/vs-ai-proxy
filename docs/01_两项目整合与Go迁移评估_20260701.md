# 两项目整合与 Go 迁移评估

## 一、项目现状分析

### 1. copilot-ollama-multi-provider-ai-proxy
- 定位：面向 Copilot / OpenAI 兼容客户端的统一多提供商代理。
- 核心能力：
  - 多提供商发现、模型映射、默认模型与候选路由。
  - OpenAI `/v1` 与 Ollama `/api/*` 双协议兼容。
  - 请求转换、流式/非流式兼容、reasoning 注入缓存。
  - 模型目录刷新、能力与上下文长度推断、超时控制。
- 技术栈：.NET 最小 API，单可执行文件，基于 `HttpClient` 转发，无独立管理界面。
- 优势：协议兼容性强、路由策略完整、配置模型选择与执行参数较成熟。
- 现状缺口：缺少可视化管理界面；依赖 .NET 运行时或自包含发布体积较大。

### 2. CopilotDeepSeek
- 定位：面向 Visual Studio Copilot 的本地 DeepSeek 代理，强调开箱可用与运行态可见性。
- 核心能力：
  - `HttpListener` 本地代理、请求日志与基本统计。
  - AES 加密本地存储 API key；支持自动运行与后台隐藏模式。
  - 简易 Web 管理界面，可查看日志、统计、设置。
- 技术栈：.NET + SQLite + 前端 portal；以 DeepSeek 单提供商为主。
- 优势：界面与本地运行体验成熟；有用户可感知的启动、设置、日志流程。
- 现状缺口：多提供商与模型路由能力弱；Windows 优先；代理逻辑较窄，主要是转发+缓存 reasoning。

### 3. llm-tester（Go 参考模版）
- 定位：多配置 LLM 测试 GUI，强调批量测试、基准测试、配置导入导出。
- 技术栈：Go + Gin + Vue3 SPA + `embed` 静态资源。
- 可借鉴点：
  - 单二进制分发；
  - SSE 流式结果输出；
  - 配置化测试工作流；
  - 前后端一体打包思路。

## 二、功能整合边界

### 建议保留
- 统一代理入口：OpenAI 与 Ollama 兼容双协议。
- 模型发现、别名、`provider/model` 路由、failover 候选机制。
- 请求转换、reasoning 缓存注入、流式转发。
- 本地配置存储与 API key 管理；可沿用 SQLite。
- Web 管理界面：设置、日志、统计、模型列表。

### 建议新增
- 多提供商统一配置页，而非仅 DeepSeek。
- 连接测试、单消息测试、批量测试与压测。
- 配置导入/导出，便于迁移和多环境切换。
- 启动向导与首次运行配置流程。

### 建议移除/简化
- CopilotDeepSeek 中面向单一 DeepSeek 的硬编码路由细节。
- 若采用 Go，可放弃 .NET 自包含发布模型，减少体积和运行时依赖。

## 三、Go 迁移必要性评估

### 迁移收益
- 单二进制分发，用户无需安装运行时，打开即用。
- 静态资源可通过 `embed` 内置，交付物更简洁。
- 并发模型与 SSE 流式输出在 Go 中实现直接，运维负担低。
- 对“减少用户安装负担、打开直接使用”的目标最匹配。

### 迁移成本与风险
- 需完整重写代理核心：路由、请求转换、模型目录、流式缓存等逻辑。
- 需重新实现前端界面；CopilotDeepSeek 的 portal 不能直接复用，需按 Gin 静态路由适配。
- 需重新建立测试与发布流程。
- 若团队主要在 .NET 生态，长期维护成本会抬高。

## 四、最优方案

### 方案 A：保留 .NET，优化单文件发布与界面融合（低风险）
- 继续基于 `copilot-ollama-multi-provider-ai-proxy` 扩展管理界面。
- 将 CopilotDeepSeek 的界面思路移植为独立前端模块。
- 通过 `dotnet publish` 自包含发布，实现接近“打开即用”。
- 优点：改动最小，核心代理能力完整保留。
- 缺点：发布体积偏大，首次下载仍需要一定时间。

### 方案 B：迁移到 Go，构建单二进制统一产品（中长期推荐）
- 以 `llm-tester` 为骨架，新增代理核心模块。
- 核心模块包括：多提供商注册、模型路由、请求转换、Ollama/OpenAI 双协议、reasoning 缓存、本地配置存储、日志统计。
- 前端使用 Vue3 SPA + `embed`，内置于二进制。
- 优点：分发与启动体验最优，跨平台一致性强。
- 缺点：需要完整实现代理核心与前端，工作量明显更大。

## 五、结论与建议

- 若当前首要目标是“快速上线可用管理界面”，选方案 A。
- 若当前首要目标是“极致轻量、打开即用、跨平台分发”，选方案 B。
- 从用户安装负担角度看，Go 单二进制是更优解；但从项目连续性看，.NET 方案可以更快落地。
- 建议先做方案 A 的最小可用版本，验证界面与配置流程；若后续用户反馈对体积和安装敏感，再启动方案 B 的迁移。
