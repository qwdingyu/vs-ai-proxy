# v0.2.16 版本发布与 Windows Smoke 踩坑记录

日期：2026-07-04

本文记录 `v0.2.16` 发布过程中出现的 GitHub Actions 双 run、Windows smoke 失败、版本显示与 Release 发布保护相关问题。内容仅基于本次本地验证、GitHub Actions run 结果和仓库代码，不包含未验证猜测。

## 1. 为什么同一个 commit 会有两个 GitHub Actions 同时跑

现象：GitHub Actions 页面中，同一个提交 `463435f` 出现两个 `build` workflow：

- `build #46`：分支 `main`，commit `463435f`。
- `build #47`：tag `v0.2.16`，commit `463435f`。

原因在 `.github/workflows/build.yml` 的触发条件：

```yaml
on:
  push:
    branches: [main]
    tags:
      - 'v*'
      - '[0-9]*'
```

本次发布流程先执行：

```bash
git push origin main
```

这会触发 `main` 分支的 workflow run。

随后执行：

```bash
git push --force origin v0.2.16
```

这会触发 tag `v0.2.16` 的 workflow run。

所以两个 Action 同时跑不是重复发布，也不是 GitHub 异常；它们是同一 workflow 被两个不同 push 事件触发。

## 2. 哪个 run 会真正发布 Release

`release` job 有额外条件：

```yaml
release:
  if: startsWith(github.ref, 'refs/tags/')
```

因此：

- `main` 分支 run 只执行检查类 job，不创建 GitHub Release。
- `v0.2.16` tag run 才会执行 `release` job 并创建 Release。

本次最终成功发布的 run 是：

- Run：`https://github.com/qwdingyu/vs-ai-proxy/actions/runs/28706490861`
- Tag：`v0.2.16`
- Head SHA：`463435f59cc774adfbed50f79f564ac55171863e`
- Release：`https://github.com/qwdingyu/vs-ai-proxy/releases/tag/v0.2.16`

## 3. 本次错误的真实原因

### 3.0 为什么之前没有 Windows smoke，以及为什么现在要加

此前的 workflow 主要包含两类检查：

- `check`：在 `ubuntu-latest` 上执行 `go vet` 和构建验证。
- `release`：tag 推送时在 Ubuntu runner 上交叉编译 Windows、macOS、Linux 的发布包。

这意味着旧流程能够证明“Windows `.exe` 可以在 Ubuntu 上交叉编译出来”，但不能证明“该 `.exe` 可以在真正的 Windows 环境中运行”，也不能覆盖 Windows runner 上的路径、PowerShell、文件锁、换行、可执行文件启动和测试顺序差异。

因此本次新增 `windows-smoke`，主要目的不是增加发布复杂度，而是补上 Windows 用户最相关的上线保护：

1. 在真实 Windows runner 上执行关键 Go 测试，提前发现跨平台差异。
2. 在真实 Windows runner 上构建并运行 `vs-ai-proxy.exe --version`，防止 Windows 包再次显示 `dev`。
3. 让 `release` 依赖 `windows-smoke`，确保 Windows 验证失败时不会创建 GitHub Release。

本次 `v0.2.16` 的失败正好证明该保护有价值：它在 Release 创建前拦住了测试中隐藏的跨平台假设，避免问题进入正式发布资产。

### 3.1 新增 Windows smoke 后暴露跨平台测试假设

`v0.2.16` 发布前新增了 `windows-smoke` job：

```yaml
windows-smoke:
  runs-on: windows-latest
```

该 job 会在 Windows runner 上执行关键测试和 Windows 二进制版本校验。它不是发布问题的根因，而是把原来只在 macOS/Linux 本地较难暴露的测试假设提前暴露出来。

失败集中在 `internal/api/api_test.go` 的模型元数据补齐测试。

### 3.2 失败 1：测试依赖跨 provider fallback 的顺序

失败日志中出现：

```text
context_length = 0xc000b00890, want 1048576
metadata should include context_length: {"found":true,"source":"model_catalog","model":"deepseek/deepseek-v4-flash","provider":"deepseek","context_length":1000000,...}
```

含义：测试期望 `deepseek-v4-flash` 一定匹配到某一个 provider 的元数据值，例如 `1048576`，但实际在 Windows runner 上匹配到了另一个 provider 的元数据值，例如 `1000000`。

原因：内置模型元数据中存在多个 provider 都声明了相同或近似模型名，例如：

- `deepseek-v4-flash`
- `deepseek/deepseek-v4-flash`
- `deepseek-ai/deepseek-v4-flash`

而测试走的是“按模型名跨 provider fallback”的路径。该路径的目标是补齐元数据，不承诺在多个 provider 候选之间固定选择某一个具体 provider 的数值。测试把不稳定的内部匹配结果当成了稳定契约。

### 3.3 失败 2：测试使用 provider_id 但配置中没有该 provider

为让测试指定 provider，曾把模型绑定到 `provider_id = "deepseek"`。随后本地测试失败：

```text
model_provider_not_found
模型 "deepseek-v4-flash" 绑定的 provider_id "deepseek" 不存在
```

原因：测试 harness 默认配置的 `providers` 是空数组。配置校验逻辑要求 `models[].provider_id` 必须指向存在的 `providers[].id`。这条校验是正确行为，不能为了测试绕过。

修复：在测试中先通过 `/api/providers` 创建 `deepseek` provider，再保存绑定 `provider_id = "deepseek"` 的模型。

### 3.4 失败 3：测试继续断言具体 profile 的 `reasoning_effort`

后续 Windows smoke 又失败：

```text
reasoning_effort = "", want medium
```

原因仍是同一类：重复模型元数据中，不同 provider profile 的可选字段不完全一致。有的 profile 有 `reasoning_effort = "medium"`，有的没有。该测试的目标是验证“缺失元数据能被补齐”，不应该断言某个非稳定候选 profile 的可选字段值。

最终修复：测试只断言稳定行为：

- `context_length` 被补齐，且为正数。
- `max_output_tokens` 被补齐，且为正数。
- `supports_tools` 被补齐为 true。
- `supports_vision` 被补齐为 false。
- metadata endpoint 返回 `found: true`，且包含 `context_length` 和 `max_output_tokens` 字段。

不再断言具体 provider fallback 产生的精确数值或可选字段。

## 4. 为什么不是生产代码错误

本次 Windows smoke 失败发生在测试断言层面，不是生产发布逻辑失败。

依据：

1. 配置校验拒绝不存在的 `provider_id` 是正确行为，且此前正是为了防止 `model_provider_not_found` 类问题。
2. 模型元数据 fallback 的生产目标是尽可能补齐模型上下文、输出长度和能力字段，不承诺重复模型名时一定选择某个 provider 的具体元数据。
3. 最终修复没有放松生产校验，也没有修改路由逻辑，只调整了测试，使其验证稳定契约而非内部候选顺序。

## 5. 发布过程中的 tag 处理

由于 `v0.2.16` 的 tag workflow 在前几次运行中失败，GitHub Release 没有成功创建。因此后续修复后使用了：

```bash
git tag -f -a v0.2.16 -m "Release v0.2.16"
git push --force origin v0.2.16
```

注意：只有在 tag 对应 Release 尚未成功发布、且明确是在修复同一个待发布版本时，才可以强制移动 tag。已经发布并被用户下载的 release tag 不应随意移动。

最终成功的提交：

```text

```

## 6. 本次新增的发布保护

### 6.1 版本号不再轻易显示 dev

程序启动时会先解析版本，再处理 `--version` 和 Web API。版本来源优先级：

1. `ldflags` 注入的 `main.version`。
2. `VS_AI_PROXY_VERSION` 环境变量。
3. Go build info 中的 module version 或 git revision。
4. 最后才回退到 `dev`。

### 6.2 CI 阻止 dev 版本进入发布链路

`check` job 中新增：

```bash
version="$(./vs-ai-proxy --version)"
test -n "${version}"
test "${version}" != "dev"
```

`.bin/release-all.sh` 中也会在打包前校验宿主平台二进制的 `--version`，如果是 `dev` 或与当前 tag/describe 不一致，直接失败。

### 6.3 Windows smoke 阻断 release

`release` job 依赖：

```yaml
needs: [check, windows-smoke]
```

这意味着 Windows 上关键测试和版本校验不过，Release 不会发布。

本次事实证明该保护是有效的：前几次失败时 Release job 被跳过，没有生成错误的 `v0.2.16` Release。

## 7. 注意事项

1. **同一个 commit 同时有 main run 和 tag run 是预期行为**。真正发布的是 tag run。
2. **不要把跨 provider fallback 的具体候选值写死到测试里**。重复模型名很多，测试应断言稳定契约。
3. **模型配置测试如果使用 provider_id，必须先创建对应 provider**。否则配置校验应该失败。
4. **已成功发布的 tag 不要强制移动**。本次可移动 tag 的前提是对应 Release 尚未成功创建。
5. **Release 资产必须由 GitHub Actions 构建**。本地 `make release` 只用于验证，不手工上传资产。
6. **`docs/images` 已删除是合理的**。FAQ 图片现在服务来源是 `web/dist/assets/images/*`，会被 `web/embed.go` 嵌入程序。
