# 近期稳定性摘要增强与诊断观测口径说明

本轮改动的目标不是改变代理链路行为，而是在 `/api/diagnostics/summary` 上补一层近期稳定性聚合，让维护者能更快判断失败是集中在 `client_gone`、`client_deadline_reached`，还是集中在 `upstream_stream_interrupted` 这类上游流中断。

## 本轮做了什么

- 在 `store` 中新增近期稳定性聚合接口，按 `provider/model/upstream` 汇总最近保留日志。
- 在诊断摘要中增加 `recent_stability`，并把最近失败的紧凑样本带回给管理面。
- 继续保留原有 `statistics`、`latest_failure`、`provider_health` 结构，不改透传、重试、熔断、fallback 逻辑。

## 2026-07-23 管理页落地（观测 UI）

- 监控页增加 **近期稳定性（只读观测）** 表格，直接渲染 `/api/diagnostics/summary` 的 `recent_stability`。
- 当任一组 `request_bytes_p95 ≥ 400KB` 时展示 **大包预警**（与代理日志 `大请求体` WARN 阈值一致，只观测不阻断）。
- `copy_summary` 标注「只读观测,不参与熔断」，并在大包组上追加预警句；`upstream_no_response` / `stream_interrupted` 文案明确 **≠ 本机未联网**（全局 `latest_failure` 与分组 `LatestFailure` 共用同一说明，避免重复两行）。
- 代理侧大包 WARN 日志补充 `provider` / `model` / `upstream`，便于与表格对齐。
- 阈值常量导出为 `proxy.LargeRequestWarnBytes`；`RequestBytes` 在 Content-Length 缺失时回退到 `upstream_bytes`，减少大包漏报。

## 2026-07-23 观测元数据最佳实践（单一事实源）

`/api/diagnostics/summary` 增加 `observation` 对象，字段包括：

| 字段 | 含义 |
| --- | --- |
| `read_only` | 恒为 true：该摘要不参与路由/熔断/重试 |
| `recent_stability_limit` | 聚合扫描的最近日志条数上限（当前 200） |
| `large_request_warn_bytes` | 与代理 WARN 同源：`proxy.LargeRequestWarnBytes` |
| `large_packet_group_count` | 近窗内 `request_bytes_p95` 达到阈值的 provider/model 组数 |

管理页前端**禁止**把 `400*1024` 当作主路径阈值，必须读 `observation.large_request_warn_bytes`；仅在 observation 缺失时使用 `FALLBACK_LARGE_REQUEST_WARN_BYTES` 兜底。`copy_summary` 的大包计数也复用同一 observation，避免前后端各算一遍。

## 为什么这样做

1. 观测逻辑应尽量和请求转发逻辑解耦。
2. 维护者需要先看到“问题集中在哪个 provider/model/upstream 组合”，再决定是否调整上游、超时、客户端设置或路由。
3. `latest_failure` 单点不足以代表一段时间内的稳定性；聚合视图更适合判断间歇性问题。

## 口径说明

- `recent_stability` 只扫描当前保留的最近日志，不扫描历史磁盘归档。
- `health check` 或不带 provider/model/upstream 归属的请求不计入模型稳定性。
- `success_rate` 只表示当前保留窗口内的成功率，不代表全量历史成功率。
- `top_error_codes`、`top_stream_states`、`top_cancel_reasons` 用于快速定位主因，不作为路由决策依据。

## 需要注意

- 这个摘要可以减少“感觉一会儿能用一会儿不能用”带来的排查成本，但不能消除真实上游链路波动。
- 如果后续要做更长期的稳定性趋势，应该把这个聚合再接到独立的历史指标存储，而不是继续往 `/diagnostics/summary` 里塞更多字段。
