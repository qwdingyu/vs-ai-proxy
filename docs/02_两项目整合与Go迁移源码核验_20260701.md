## 1. 结论先行

建议继续以 `vs-ai-proxy` 的 Go 实现作为最终产品底座，但不能把当前 Go 版视为已达到 `copilot-ollama-multi-provider-ai-proxy` 的核心能力。当前 Go 版已经具备单二进制方向、嵌入式前端、管理 API、基础代理、基础 provider registry、基础流式转发、请求日志统计等雏形；真正缺的是把这些 Module 接成适合 Visual Studio Copilot 的可靠产品链路。

`copilot-ollama-multi-provider-ai-proxy` 应作为行为基准和核心 Module 的移植来源，尤其是：

- provider 能力注册表与 provider 发现
- 模型目录刷新、模型选择、模型别名、provider 优先级和 failover
- OpenAI `/v1/*` 与 Ollama `/api/*` 双协议
- SSE 与 NDJSON 双向流式转换
- reasoning_content 缓存与注入
- 按 provider 能力治理请求参数
- Visual Studio BYOM/Copilot 场景下的模型展示信息

`CopilotDeepSeek` 只建议作为 UI 信息架构和本地运行体验参考，不建议作为代理核心参考。它的 README 明确是 DeepSeek 单 provider 场景，源码也围绕单一 `_targetBase` 与 `_apiKey` 做转发；这与“兼容更多大模型 API provider”的目标不匹配。

`llm-tester` 适合作为 Go 单二进制、配置 CRUD、导入导出、连接测试、批量测试、SSE 测试台的模板，不适合作为 Visual Studio Copilot 代理核心。它的 `llm.Provider` Interface 主要是 TestConnection/Chat/ListModels，并且共享请求构造明确强制 `stream=false`，这是测试台语义，不是 Copilot 代理语义。

## 3. 当前 `vs-ai-proxy` 的源码现状

### 3.1 已经具备的 Module

当前 Go 项目的核心 Module 分布如下：

- 进程装配：`cmd/server/main.go`
- 代理入口：`internal/proxy/server.go`
- 管理 API：`internal/api/api.go`
- 配置持久化：`internal/config/config.go`
- provider Interface/Adapter：`internal/provider/provider.go`
- provider 能力注册表：`internal/provider/capabilities.go`
- provider registry：`internal/provider/registry.go`
- OpenAI/Ollama 转换：`internal/converter/ollama_openai.go`
- 请求日志和统计：`internal/store/store.go`
- 前端嵌入：`web/embed.go` + `web/dist/index.html`

当前主程序会创建代理服务、管理 API 服务和嵌入式前端，但只启动一个 HTTP Server。默认端口为 `12345`，根路径承载 Visual Studio/OpenAI/Ollama 兼容代理，Web 管理面板挂载在 `/admin`，管理 API 挂载在 `/admin/api/*`。

### 3.2 当前前端状态

必须明确：`/Users/dingyuwang/0-X/0-x/vs-ai-proxy/web` 是前端，不是后端。

源码证据：

- `web/embed.go:8-18` 将 `dist` 嵌入 Go 二进制。
- `web/dist/index.html:51-57` 有前端导航：提供商、模型、日志。
- `web/dist/index.html:61-97` 有快速状态和最近日志。
- `web/dist/index.html:99-138` 有 provider 管理界面。
- `web/dist/index.html:140-174` 有 model 管理界面。
- `web/dist/index.html:176-196` 有日志界面。
- `web/dist/index.html` 通过 `API_BASE = '/admin/api'` 调用后端管理 Interface，避免和根路径 Ollama `/api/chat`、`/api/tags` 等协议端点冲突。

当前前端的真实缺口不是“没有 UI”，而是：

- 没有发现可维护的前端源码工程，只看到打包后的 `index.html`。
- provider 类型只有 OpenAI/Ollama/Custom 的基础选择，尚未体现 C# 版 provider capability registry 的全部能力字段。
- 保存 provider/model 后，当前管理 API 主要更新配置文件和本地缓存，没有把 proxy registry 热更新到生产路由链路。

### 3.3 当前 Go 版最重要的 P0 缺口

#### P0-1：模型目录 discovery 与 `/v1/models`、`/api/tags` 没有真正接通

这是本次源码核验发现的关键问题。

证据：

- `internal/proxy/server.go:82-103` 的 `refreshModels` 会调用 provider 的 `ListModels`，并把结果写入 `entry.Models`。
- `internal/provider/registry.go:149-163` 的 `AllModels()` 只读取 `modelToProvider` 的 key，不读取 `entry.Models`。
- `internal/provider/registry.go:117-135` 有 `UpdateModelMappings*`，但 `rg` 没发现任何调用点。
- `internal/provider/registry.go:196-207` 有 `RefreshIfNeeded()`，但同样没有调用点。
- `/v1/models` 和 `/api/tags` 分别在 `internal/proxy/server.go:494-535` 调用 `registry.AllModels()`。

推论：即使启动时异步发现了上游模型，模型列表也可能不会出现在 Visual Studio 可选模型列表里。`ResolveCandidates` 的 fallback 会扫描 `entry.Models`，所以某些已知模型的 chat 路由可能还能工作，但模型发现展示链路不完整。

这比“缺少定时刷新”更严重：当前是 discovery 结果与 catalog Interface 没有稳定接线。

#### P0-2：Ollama 协议流式方向不完整

当前 Go 版不是完全没有流式，但不满足 Visual Studio/Ollama 兼容的完整矩阵。

证据：

- `/api/chat` 在 `internal/proxy/server.go:349-356` 如果 `stream=true`，直接调用 `handleStream`。
- `handleStream` 在 `internal/proxy/server.go:394-409` 只按 provider 上游格式分流，不知道客户端入口是 `/v1/chat/completions` 还是 `/api/chat`。
- `streamOpenAI` 在 `internal/proxy/server.go:419` 设置 `Content-Type: text/event-stream`。
- `streamOllamaToOllama` 在 `internal/proxy/server.go:446-456` 注释写“转换为 OpenAI SSE 格式”，实际也设置 `Content-Type: text/event-stream`。
- 但 C# 版 `/api/chat` 在 `OllamaEndpoints.cs:222-240` 对 Ollama provider 流式返回 `application/x-ndjson` 并 passthrough；在 `OllamaEndpoints.cs:301-323` 对 OpenAI 上游也返回 `application/x-ndjson`。

推论：Go 版 `/api/chat` 的流式响应格式当前不等价于 C# 版，也不等价于原生 Ollama NDJSON。Visual Studio BYOM 如果走 Ollama surface，这会是致命兼容问题。

另一个源码风险：`converter.ParseOllamaStreamChunk` 在 `internal/converter/ollama_openai.go:12-31` 要求每行以 `data:` 开头，但原生 Ollama 流通常是 NDJSON 行。当前 Go 版 Ollama upstream 转 OpenAI SSE 的解析逻辑需要重新核验和测试。

#### P0-3：ProviderCapabilities 已存在，但 ChatPath 没有完整接入 provider Adapter

Go 版已经有 provider 能力注册表，不应该重复造一个浅 Module。但它现在没有产生足够 Leverage。

证据：

- `internal/provider/capabilities.go:98-106` 为 Google 配置了 `v1beta/openai/chat/completions` 和 `v1beta/openai/models`。
- `internal/provider/provider.go:155-220` 的 `OpenAIProvider.Chat` 和 `ChatStream` 硬编码 `p.BaseURL+"/v1/chat/completions"`。
- `internal/provider/provider.go:222-260` 的 `ListModels` 硬编码 `p.BaseURL+"/v1/models"`。

推论：虽然 registry 里声明了不同 provider 的 path，但 OpenAIProvider Adapter 并不消费 ChatPath/ModelsPath。Google 这类非标准 path provider 会在实际 chat/list models 时失败或走错路径。

#### P0-4：provider 优先级与 failover 没有达到 C# 版语义

Go 版有 candidates 循环，不是单 provider。但是它没有等价实现 C# 的优先级策略。

证据：

- `internal/config/config.go:10-18` 明确 `Priority` 当前仅 UI 展示用。
- `internal/provider/registry.go:66-115` 的 `Candidate.Priority` 是内部固定值 0/1/2，不是来自配置。
- C# 版 `ModelCatalogService.cs:86-135` 会按模型 selection priority 与 provider order 排序，并构建 `upstreamToProviders`，再调用 `ProviderRegistry.UpdateModelMappings`。
- C# 版 `ProviderRegistry.cs:155-180` 的 `ResolveCandidates` 明确 bare model 返回按配置优先级排序的 provider 候选。

推论：Go 版的 failover 是“有循环”，但不是“产品级多 provider 候选 + 优先级排序 + provider-qualified alias”。

#### P0-5：代理认证缺失

重点参考项目支持可选代理认证：

- `Program.cs:30` 读取 `PROXY_API_KEY`。
- `Infrastructure/ProxyAuthenticationMiddleware.cs:1-28` 在设置 key 后要求 `Authorization: Bearer ...`。

当前 Go 版没有发现等价的代理认证 middleware。provider upstream 的 API key 不能替代本地代理认证。生产环境下本地端口如果被其他进程或局域网访问，风险很直接。

#### P0-6：reasoning_content 缓存与注入缺失

C# 版的核心价值之一是让推理模型在多轮对话中更稳定：

- `RequestTransformer.cs:183-269` 会把缓存的 `reasoning_content` 注入 assistant 消息，并清理空 assistant placeholder。
- `ChatStreamingService.cs:13-126` 从 OpenAI SSE 中缓存 reasoning。
- `ChatStreamingService.cs:147-260` 在 OpenAI SSE 转 Ollama NDJSON 时同样缓存 reasoning。

当前 Go 版没有发现独立 ReasoningCache Module，也没有在 converter/streamer 中做 reasoning cache 注入。对 DeepSeek-R1、Kimi、Qwen reasoning 等模型，这不是锦上添花，而是 Copilot 多轮体验的核心能力。

#### P0-7：管理 UI 修改配置后没有热更新代理路由

证据：

- `internal/api/api.go:149-163` 的 `saveConfig` 注释明确“不直接热重启 proxy server”。
- `internal/api/api.go:170-231` 的 provider/model 增删改主要修改 `s.config` 和 `configMgr.Save`。
- 当前没有看到管理 API 调用 `proxy.Server` 重新注册 provider、重建 registry、刷新 model catalog。

推论：UI 上保存 provider 不等于 Visual Studio 请求立即路由到新 provider。对产品而言，这会造成“配置页显示成功但 Copilot 不生效”的高风险体验。

## 4. 重点参考项目 `copilot-ollama-multi-provider-ai-proxy` 的核心能力

该项目应作为代理核心行为的主要参考，而不是 CopilotDeepSeek。

### 4.1 明确面向 Visual Studio Copilot/BYOM

源码和文档中多处说明其 primary use case 是 Visual Studio 2026 内的 GitHub Copilot。`docs/AGENTS.md` 和 `CLAUDE.md` 都强调 Visual Studio 2026 Copilot coding workload。虽然该项目也兼容 Cursor、Continue.dev、OpenAI SDK 和 Ollama 客户端，但本项目整合时应以 Visual Studio 为目标验收面。

### 4.2 ProviderCapabilitiesRegistry 是新增 provider 的主 seam

`Services/ProviderCapabilitiesRegistry.cs:1-8` 明确写出：新增 provider 只需要 registry entry 和 `config/model-selection/{provider}.json`。

当前注册 provider：

- deepseek
- openai
- moonshot
- google
- cerebras
- nvidia
- openrouter
- groq
- zenmux
- ollama

每个 provider 声明：

- provider category
- API format：OpenAI 或 Ollama
- 是否支持 reasoning_effort
- 是否支持 top_k
- ChatPath
- ModelsPath
- DefaultBaseUrl
- EnvPrefix

Go 版也有类似数据结构，但应该把它从“声明表”深化成真正的 provider Adapter seam：Chat、ChatStream、ListModels、参数治理、模型发现都必须消费同一份 capabilities。

### 4.3 ModelCatalogService 是 Visual Studio 模型列表的核心 Module

C# 版 `ModelCatalogService.cs:31-142` 的职责很清晰：

- 从每个 provider 拉取模型列表。
- 按 `config/model-selection/*.json` 过滤可展示模型。
- 计算 provider/model 的优先级。
- 给每个 provider 生成 `model@provider` qualified alias。
- 对 bare model 选择优先级最高的 winner。
- 构建 upstream model 到多个 provider 的 failover map。
- 定时 5 分钟刷新。

这正是当前 Go 版缺失的深 Module。Go 版不应该把 model discovery、provider registry、UI model config 分散在多个浅实现里，而应该引入一个 Go 版 `ModelCatalog`，由它唯一负责 Visual Studio 看到什么模型、请求路由到哪个 upstream、候选 provider 怎么排序。

### 4.4 RequestTransformer 是 provider 兼容性的核心 Module

C# 版 `RequestTransformer.cs:15-141` 做了几件 Go 版当前没有做完整的事：

- 读取模型执行配置。
- 按 provider capabilities 判断是否支持 `reasoning_effort`。
- 按 provider capabilities 判断是否支持 `top_k`。
- 对 native reasoner 避免同时注入 `temperature` 和 `top_p`。
- 支持 `override_client_params`，对有硬性参数要求的模型强制覆盖 client 参数。
- 只在安全条件下注入参数，不是无脑追加字段。

当前 Go 版 `internal/proxy/server.go:571-595` 只处理 `temperature` 和 `max_tokens` 默认值。对“兼容更多大模型 API provider”来说，这是不够的，因为 provider 之间真正的差异往往不是 URL，而是参数接受范围、stream dialect、错误格式、模型名格式和工具调用字段。

### 4.5 ChatStreamingService 是流式兼容的核心 Module

C# 版把流式处理集中在 `ChatStreamingService`：

- `StreamAndCache`：OpenAI SSE passthrough，并缓存 reasoning。
- `StreamNdjsonPassthrough`：Ollama NDJSON passthrough。
- `StreamOllamaAndCache`：OpenAI SSE 转 Ollama NDJSON，并缓存 reasoning。

当前 Go 版的 stream seam 太粗，只看 provider 上游格式，不看 client surface。建议拆成明确矩阵：

| Client surface | Upstream format | 正确输出 |
| --- | --- | --- |
| `/v1/chat/completions` | OpenAI SSE | OpenAI SSE passthrough + reasoning cache |
| `/v1/chat/completions` | Ollama NDJSON | Ollama NDJSON -> OpenAI SSE |
| `/api/chat` | Ollama NDJSON | Ollama NDJSON passthrough |
| `/api/chat` | OpenAI SSE | OpenAI SSE -> Ollama NDJSON |

这个矩阵是 Visual Studio 兼容性的 P0。

`CopilotDeepSeek` 的 README 明确说明它是让 Visual Studio Copilot 使用 DeepSeek 的本地代理：

源码中可借鉴的只是本地产品体验：

- `ProxyServer.cs:191-200` 有 start/stop 控制。
- `ProxyServer.cs:210-221` 有请求 stats/logs API。
- `SettingsService.cs:61-72` 面向 Web 界面隐藏 API key。

## 6. `llm-tester` 的可借鉴点和不可借鉴点

`llm-tester` 是 Go 单二进制产品化模板，不是 Visual Studio Copilot 代理模板。

可借鉴：

- `cmd/llm-tester/main.go:1-15` 明确 Go + Gin + Vue3 SPA + `go:embed`，配置持久化、SSE 测试结果、SPA fallback。
- `cmd/llm-tester/main.go:90-108` 有配置、测试、日志 API 分组。
- `cmd/llm-tester/main.go:170-191` 有配置导入导出。
- `cmd/llm-tester/main.go:194-215` 有连接测试。
- `storage/store.go:1-14` 采用用户目录 JSON、0600 文件、原子写入、互斥锁。

不可直接借鉴为代理核心：

- `llm/provider.go:69-85` 的 Provider Interface 只有 TestConnection/Chat/ListModels，不包含 proxy pass-through、client surface、stream dialect。
- `llm/provider.go:193-211` 的 `BuildChatBody` 强制 `stream=false`，这是为了测试台避免 SSE 阻塞，不适合 Copilot 代理。

建议把 `llm-tester` 的能力作为 `vs-ai-proxy` 管理端的“测试实验室”：

- provider 连接测试
- 单轮 chat 测试
- 批量模型探测
- 延迟基准
- burn test
- 配置导入导出

这些功能不应污染代理核心 Module。

## 7. 推荐的 Go 架构

目标不是把 C# 文件逐行翻译成 Go，而是把 C# 项目里已经证明有 Leverage 的 Module 迁移成 Go 的深 Module。

### 7.1 推荐 Module 切分

| Module | Interface 应该承诺什么 | 来源参考 |
| --- | --- | --- |
| ProviderCapabilities | 给定 provider name，返回 API format、auth、chat path、models path、参数能力、stream dialect、默认 base URL。 | C# `ProviderCapabilitiesRegistry`，Go `capabilities.go` |
| ProviderAdapter | 按 capabilities 执行 Chat、ChatStream、ListModels；不得硬编码 `/v1/*`。 | Go `provider.go` 需要加深 |
| ModelCatalog | 生成 Visual Studio 可见模型、provider-qualified alias、upstream 映射、failover candidates、定时刷新。 | C# `ModelCatalogService` |
| RequestTransformer | 替换 upstream model，过滤/注入参数，注入 reasoning_content，清理不合法 message。 | C# `RequestTransformer` |
| StreamTranslator | 按 client surface 和 upstream format 做 SSE/NDJSON 矩阵转换并缓存 reasoning。 | C# `ChatStreamingService` |
| ReasoningCache | 缓存 reasoning_content，按 assistant index/toolcall id 注入下一轮请求。 | C# `ReasoningCacheService` + CopilotDeepSeek 思路 |
| ProxyAuth | 可选 `PROXY_API_KEY` Bearer 认证。 | C# `ProxyAuthenticationMiddleware` |
| ConfigStore | provider/model/secret/log 的持久化。可先 JSON，后 SQLite。 | Go `config.Manager`、llm-tester store、CopilotDeepSeek SQLite |
| ManagementUI | provider 配置、模型配置、日志、统计、测试、导入导出、Visual Studio 配置向导。 | 当前 `web` + CopilotDeepSeek portal + llm-tester |

### 7.2 Provider 兼容性策略

为了“兼容更多大模型 API provider”，新增 provider 不应要求修改代理 handler。建议 provider registry 至少支持这些字段：

- `name`
- `display_name`
- `api_format`: `openai` / `ollama`
- `category`: direct / multi-model / aggregator
- `base_url`
- `chat_path`
- `models_path`
- `auth_type`: bearer / none / api-key header
- `env_prefix`
- `supports_reasoning_effort`
- `supports_top_k`
- `supports_tools`
- `supports_vision`
- `stream_format`: openai_sse / ollama_ndjson
- `default_headers`: 例如 OpenRouter 可能需要应用标识类 header
- `model_selection`: 启用模型、优先级、执行参数、上下文长度、最大输出、override mode

当前应至少覆盖并验收这些 provider：

- DeepSeek
- OpenAI
- Moonshot/Kimi
- Google Gemini OpenAI-compatible surface
- Cerebras
- NVIDIA NIM
- OpenRouter
- Groq
- ZenMux
- Ollama local
- Ollama Cloud

未来新增 provider 时，理想路径是“新增 registry/config + 测试”，而不是改 `/v1/chat/completions` handler。

## 8. 是否有必要改到 Go

结论：如果核心目标是“减少用户安装负担，下载后打开直接使用”，Go 是合理且建议继续推进的方向；但必须承认当前 Go 版仍缺少 C# 版的关键生产能力。

### 8.1 Go 的必要性成立的条件

Go 迁移/继续 Go 化有价值，是因为：

- 单二进制分发更符合普通 Visual Studio 用户的预期。
- `web/embed.go` 已经证明可以把前端打进二进制。
- 当前仓库已经有 Go 代理和管理 API 雏形，不是从空白开始。
- Visual Studio 用户配置本地 endpoint 时，最重要的是稳定运行和少安装依赖。

### 8.2 Go 不应该解决的问题

Go 本身不会自动解决：

- Visual Studio/Copilot 协议兼容
- provider 参数差异
- SSE/NDJSON 转换
- reasoning 缓存
- 模型 catalog 和 alias
- provider failover
- API key 安全存储
- UI 配置热生效

这些要靠架构和测试补齐，不能靠语言迁移获得。

### 8.3 推荐路线

不建议重写成 `llm-tester`。建议以当前 `vs-ai-proxy` 为底座：

1. 保留 Go proxy + management API + web embed。
2. 以 `copilot-ollama-multi-provider-ai-proxy` 为行为基准，迁移 ModelCatalog、RequestTransformer、StreamTranslator、ReasoningCache、ProxyAuth。
3. 以 `CopilotDeepSeek` 和 `llm-tester` 改造管理 UI，而不是让 UI 决定代理核心。
4. 先完成 Visual Studio Copilot P0 验收，再扩展批量测试和图表。

## 9. 实施优先级

### P0：Visual Studio Copilot 可用前必须完成

1. 修复 ModelCatalog 接线：发现模型后必须更新 `modelToProvider`、`modelToUpstream`、`upstreamToProviders`，并让 `/v1/models`、`/api/tags` 使用同一 catalog。
2. 实现 provider priority 和 failover：支持 bare model 多 provider 候选，支持 `model@provider` 精确路由。
3. 修复流式矩阵：`/v1` 输出 SSE，`/api/chat` 输出 NDJSON，按 client surface 与 upstream format 双维度转换。
4. 让 ProviderAdapter 使用 capabilities 的 `ChatPath` 和 `ModelsPath`，不能继续硬编码 `/v1/chat/completions` 与 `/v1/models`。
5. 增加可选 `PROXY_API_KEY` Bearer 认证。
6. 移植 RequestTransformer：模型替换、参数过滤、reasoning_effort/top_k/top_p 治理、override_client_params。
7. 移植 ReasoningCache：非流式和流式都要缓存并在下一轮注入。
8. UI 配置保存后要热更新 proxy registry，或者明确提示需要重启并提供一键重启。生产体验上推荐热更新。
9. 补最小测试集：模型 catalog、provider path、OpenAI SSE passthrough、Ollama NDJSON passthrough、SSE->NDJSON、NDJSON->SSE、failover、auth。

### P1：产品竞争力

1. 管理 UI 增加 provider capability 可视化：path、api format、参数能力、模型 selection priority。
2. 增加 Visual Studio 配置向导：本地 endpoint、Resource Endpoint、模型 ID、token limit、tool calling/vision 开关提示。
3. 引入配置导入导出，参考 `llm-tester`。
4. 增加 provider 连接测试、单轮 chat 测试、批量模型探测。
5. 日志和统计从纯内存升级为可持久化；如要记录请求历史和筛选，SQLite 比 JSON 更合适。
6. API key 存储至少要避免明文直接展示；可先掩码，后续再做 OS keychain 或本机加密。

### P2：产品化增强

1. Dockerfile 和 compose。
2. release 脚本和跨平台构建。
3. provider 延迟趋势、错误率、分 provider/model 过滤。
4. burn test、benchmark、并发压测。
5. 自动检查 Visual Studio endpoint 配置可达性。

## 10. 验收标准

面向 Visual Studio，不应只用 curl 测 `/v1/chat/completions` 就算完成。建议 P0 验收包含：

- Visual Studio 能发现模型列表，模型列表来自 `/api/tags` 或 `/v1/models` 时都可路由。
- Visual Studio 选择 bare model 时走默认优先 provider，选择 `model@provider` 时走指定 provider。
- 一个 provider 失败时，非流式请求能按候选 provider failover。
- 流式请求在未写出任何字节前失败可以尝试下一个 provider；一旦开始写出，必须正确结束或上报。
- `/api/chat stream=true` 返回 Ollama NDJSON，不返回 OpenAI SSE。
- `/v1/chat/completions stream=true` 返回 OpenAI SSE。
- reasoning 模型多轮对话能保留 reasoning_content，不破坏 tool calls。
- 未设置 `PROXY_API_KEY` 时本地开放；设置后无 Bearer token 返回 401。
- UI 保存 provider 后，Visual Studio 请求能立即使用该 provider，或 UI 明确要求重启。

## 11. 剩余风险和待确认项

- Visual Studio 当前具体使用 `/v1` 还是 `/api` surface，两个参考项目给出了不同线索：`CopilotDeepSeek` README 配置 Resource Endpoint 为 `/v1`，`copilot-ollama` 同时强化 `/api/tags` 的 BYOM 模型列表。因此 Go 版必须保留双协议，不能只做其中一个。
- 当前 `web` 只有 `dist/index.html`，如果后续要长期演进 UI，需要决定是否引入真正的前端源码工程；否则修改会集中在一个大 HTML 文件里，Locality 较差。
- API key 存储方案未定。JSON 简单但密钥安全弱；SQLite 适合日志/统计；OS keychain 更安全但跨平台工作量更高。
- C# 测试数量本次只做源码计数，没有执行 `dotnet test`。后续如果要把 C# 项目作为行为 oracle，应先跑通它的测试，再移植成 Go 测试。
- 当前 Go `store.Store` 有 `PersistToFile/LoadFromFile`，但主启动路径没有看到接线；日志/统计重启后是否保留不能假设为已实现。

## 12. 最终建议

以 `vs-ai-proxy` 继续 Go 化是正确方向，但下一步不应先美化 UI，也不应先扩展更多 provider 名称。正确顺序是先把 `copilot-ollama-multi-provider-ai-proxy` 的核心代理行为迁移成 Go 的深 Module：

1. ModelCatalog
2. StreamTranslator
3. RequestTransformer
4. ReasoningCache
5. ProviderCapabilities 驱动的 ProviderAdapter
6. ProxyAuth
7. Visual Studio 验收测试

等这些 P0 完成后，再把 `CopilotDeepSeek` 的本地体验和 `llm-tester` 的测试台能力整合进管理 UI。这样既能保持 Go 单二进制的安装优势，又不会牺牲 Visual Studio Copilot 的核心兼容性。

## 21. 本轮实现进度更新（2026-07-02，流式 failover 写出边界）

### 21.1 已完成并验证的新增项

   - `/v1/chat/completions stream=true` 中，如果某 provider 在写出前失败，仍允许 failover。
   - 如果某 provider 已写出部分 SSE 后失败，当前请求直接结束，不再尝试后续 provider。

### 41.3 当前建议的上线判断

如果“上线”指的是 Go 版代码层面已经达到可试运行状态，那么现在是接近可试运行的，前提是继续做一轮 Visual Studio 真机验收。

如果“上线”指的是对外宣称已经完成 Visual Studio 端到端闭环，那么现在还不能这么说，因为最后一段客户端验证还没有在这里实际执行。

### 41.4 Visual Studio 端到端验收清单

建议下一轮只做这 5 件事，不再扩散：

1. 启动 Go 代理，确认 `/health`、`/v1/models`、`/api/tags` 正常返回。
2. 在 Visual Studio 里把 Copilot / BYOM 资源端点指向本地代理，确认能看到模型列表。
3. 选一个 bare model 和一个 `model@provider` 模型，分别确认默认路由与显式路由都正确。
4. 发起一次流式聊天，确认客户端收到的是它期望的 surface 格式。
5. 故意让首个 provider 失败，确认能在未开始输出时切到备用 provider。

## 42. 本轮实现进度更新（2026-07-02，C# 参考边界与 UseAI 内置源）

本轮重点核对两个问题：一是当前实现有没有为了照搬 C# 而偏离产品目标；二是把自有 OpenAI-compatible 源 `UseAI` 作为默认第一 provider 接入。

### 42.1 是否存在生搬硬套

当前没有发现明显“为了照搬 C# 结构而牺牲 Go 产品目标”的问题。原因如下：

1. C# 项目主要被当作行为基准，而不是逐类翻译。
   - Go 版保留的是 Visual Studio / Copilot 需要的协议行为：模型发现、OpenAI/Ollama 双 surface、流式转换、provider failover、reasoning 缓存、请求参数治理。
   - 没有照搬 ASP.NET endpoint、C# service class 分层或 .NET hosting 细节。

2. Go 版已经形成自己的产品结构。
   - `ProviderCapabilities` 负责 provider 差异。
   - `Registry` 负责模型到 provider 候选解析和优先级。
   - `ModelCatalog` 负责 Visual Studio 可见模型与 provider-qualified alias。
   - `RequestTransformer` 负责按 provider 能力过滤和注入参数。
   - `web/dist/index.html` 与管理 API 形成本项目自己的 Web 面板闭环。

3. 目前保留 C# 行为的地方是合理的。
   - SSE / NDJSON 流式矩阵是 Visual Studio 兼容的核心能力，不是多余迁移。
   - provider capability registry 是兼容更多 API provider 的必要抽象。
   - reasoning cache 对 DeepSeek-R1、Kimi、Qwen 等推理模型体验有实际价值。

### 42.2 仍缺的 Visual Studio 专项能力

当前主要缺口仍然集中在真实客户端验收，而不是 Go 代码里缺某个已知 handler：

1. 还没有在目标 Visual Studio Copilot/BYOM 环境中确认真实握手路径。
2. 还没有确认 Visual Studio 实际优先使用 `/v1/models`、`/api/tags` 还是两者组合。
3. 还没有拿 Visual Studio 真实请求样本反查是否需要额外支持 Responses API、特殊 headers 或额外 metadata。
4. Web 面板还缺 Visual Studio 配置向导，例如本地 endpoint、推荐模型 ID、认证 token 和故障排查提示。
5. 当前测试台能验证 provider 连接和 chat，但还不是 Visual Studio 等价请求回放器。

### 42.3 UseAI 内置源接入决策

已将 `UseAI` 作为第一方内置 provider 接入：

1. 内置名称：`UseAI`。
2. OpenAI-compatible base URL：`https://api.eforge.xyz/v1`。
3. provider 能力注册名：`useai`。
4. 默认配置中排在第一位，`priority=0`。
5. 旧配置文件加载和 Web 保存配置后，也会自动把 `UseAI` 放回 provider 列表第一位。
6. 不再通过 `PROVIDER_USEAI_API_KEY` / `PROVIDER_USEAI_BASE_URL` 注入大模型配置；UseAI 的 API key、base_url 和启用状态统一由 Web 面板写入 `config.json`。
7. 旧配置文件加载和 Web 保存配置时会保留用户已写入 `config.json` 的 UseAI key/base_url，但 `.env` 不再作为大模型 provider 配置源。

当前没有写死任何 API key。原因是客户端二进制里写死 key 会让额度控制、泄露处置和灰度策略变得不可控。更合理的产品方式是：程序内置 provider 和默认 URL，额度凭证通过 Web 面板、安装器生成配置或后续账号体系注入 `config.json`。

## 43. 本轮实现进度更新（2026-07-03，单端口与 `/admin` 管理面板）

为降低用户安装与理解成本，当前实现已从“代理端口 + 管理端口”收敛为单端口：

1. 默认端口改为 `12345`，推荐环境变量为 `PORT=12345`。
2. 主程序只启动一个 HTTP Server。
3. `/admin` 和 `/admin/*` 分发到 Web 管理端。
4. `/admin/api/*` 是管理 API 前缀，前端 `API_BASE` 已改为 `/admin/api`。
5. 根路径 `/v1/*` 继续保留 OpenAI-compatible 代理协议。
6. 根路径 `/api/chat`、`/api/tags`、`/api/show`、`/api/version` 继续保留 Ollama-compatible 代理协议，避免 Visual Studio / BYOM 发现路径被管理 API 抢占。
7. 旧 `PROXY_PORT` 仍作为兼容 fallback；`MANAGEMENT_PORT` / `MANAGEMENT_HOST` 对主程序已废弃，启动时只提示警告，不再创建第二个监听端口。
8. 本机二进制默认绑定 `127.0.0.1`；Docker 容器内部绑定 `0.0.0.0`，但 compose 默认只发布到宿主机 `127.0.0.1:${PORT:-12345}`，避免把能读写 API key 的 `/admin` 暴露到局域网。
9. 管理 API 支持 `ADMIN_API_KEY` Bearer 鉴权；如果未设置 `ADMIN_API_KEY` 但设置了 `PROXY_API_KEY`，管理 API 会复用 `PROXY_API_KEY`。前端在收到 401 时会提示输入 token 并写入浏览器 `localStorage`。
