## 2. 逐提交审查

### 2.1 c9757e7 — "Prevent unstable upstream failures from being misreported or replayed"

**改动规模**：48 文件，+3122/-78 行，是本轮最大提交。

**核心变更**：

| 变更 | 文件 | 重要性 |
|------|------|--------|
| 新增 `UpstreamAttempt` / `upstreamTransportError` 结构化类型 | `provider.go` | 最关键 |
| 新增 httptrace 阶段追踪 (`upstreamHTTPTrace`) | `provider.go` | 最关键 |
| 收紧 provider 内部重试边界 (`isRetryableUpstreamTransportError`) | `provider.go` | 高 |
| 新增 `recent_stability` 稳定性摘要 | `store.go`, `api.go` | 中 |
| 大请求矩阵诊断脚本 | `tests/large_request_matrix_diagnostic.sh` | 中 |

**架构亮点**：

1. **阶段机设计**（`provider.go:upstreamHTTPTrace`）
   ```go
   upstreamStagePreparing → resolving_dns → connecting → tls_handshake
   → writing_request → waiting_response_headers → receiving_response_headers
   ```
   使用 `atomic.Int32` CAS 保证阶段只能向前推进。每个 HTTP 重定向 `GetConn` 回调会重置为 `preparing`，避免跨 hop 污染。

2. **重试安全边界**（`provider.go:isRetryableUpstreamTransportError`）
   - 允许短重试：`preparing_request`, `resolving_dns`, `connecting`, `tls_handshake`
   - 禁止重试：`writing_request`, `waiting_response_headers`, `receiving_response_headers`
   - 原则：chat POST 非幂等，请求写出后上游可能已接收，代理层不能再重放

3. **两层尝试记录**
   - `attemptDiagnostic`：proxy 层候选 provider 切换（外层）
   - `upstreamAttemptDiagnostic`：同一 provider 内部短重试（内层）
   - 两层分开使得日志可以判断"是换了 3 个 provider 还是同一个 provider 内部重试了 3 次"

**审查意见**：

✅ **正确做法**：空 `Idempotency-Key` 决定不使用。Go 标准库会把带该 header 的 POST 视为可重放，即使零长度 slice 不发到上游也会改变本地语义。文档 `40_*` 中对此有详细踩坑记录。

✅ **正确做法**：`providerOperationContext` 继承调用方 deadline 而非覆盖。该函数检查 `parent.Deadline()` 后仅在无 deadline 时才设置 60s 默认超时，确保模型配置的长超时不会被 provider 层截断。

⚠️ **注意点**：`isRetryableConnectionBreak` 使用字符串匹配判断网络错误类别（`strings.Contains(lower, "eof")` 等），这是 Go 生态中的常见做法但存在跨版本/跨平台脆弱性。函数已通过 `isRetryableUpstreamTransportError` 的门禁限制了适用阶段（仅在连接建立前生效），因此即使误匹配也不会导致危险重放。建议后续考虑使用 `net.Error` 接口的 `Temporary()` 方法做更稳健的判断。

### 2.2 ab24780 — "Prevent upstream failures from being mislabeled as client disconnects"

**改动规模**：3 文件，+386/-2 行。

**核心变更**：`finalizeRequestStatus` 增加条件判断，当 handler 已设置明确错误状态（4xx/5xx 或 `X-Proxy-Error-Code` 响应头）时，不再因 request context 关闭而覆盖为 `client_gone`。

**审查意见**：

✅ **关键修复**：流式场景下，上游在 `waiting_response_headers` 阶段断开时，Go 的 HTTP client 会返回 context 错误，之前的代码会在 `finalizeRequestStatus` 中无条件标记为 `client_gone`。这导致了用户日志中反复出现的误导性诊断——明明是上游问题却被说成"客户端取消"。

✅ **防护充足**：新增的测试 `TestUpstreamNoResponseNotMislabeledAsClientGone` 覆盖了挂起上游 + 代理超时场景，验证了 `error_code=upstream_no_response` 和 `cancel_reason=""` 的正确性。

### 2.3 2c15c34 — "Stop replaying already-submitted upstream 5xx"

**改动规模**：3 文件，+18/-1 行。

**核心变更**：`shouldRetryOpenAIProviderError` 中，5xx 仍然允许短重试（这是保留的防御行为），但重试逻辑在 `ChatRaw`/`ChatStream` 的重试循环中已经受到阶段约束——如果错误携带了 `upstreamTransportError` 且 stage 为 `writing_request` 之后的阶段，`shouldRetryOpenAIProviderError` 会通过 `isRetryableUpstreamTransportError` 返回 false。

**审查意见**：

✅ **正确**：这个提交在文档中总结为"Stop replaying already-submitted upstream 5xx"，实际上是通过 `isRetryableUpstreamTransportError` 的阶段判断实现的。对于透传的 5xx HTTP 错误（`providerHTTPError`），仍然允许短重试——这是正确的，因为 new-api/sub2api 的 503 可能是某个渠道临时不可用。

### 2.4 0f1b0d3 — "fix: record partial stream failures and tighten recovery boundaries"

**改动规模**：92 文件，+6800/-639 行（大部分是 soak 测试数据文件）。

**核心变更**：

| 变更 | 文件 | 重要性 |
|------|------|--------|
| 新增 `recovery_policy.go`（恢复边界集中管理） | `recovery_policy.go` | 高 |
| 新增 `recovery_policy_test.go`（边界矩阵测试） | `recovery_policy_test.go` | 高 |
| `markWrittenStreamFailure` 记录半截流失败 | `server.go`, `recovery_policy.go` | 高 |
| ollama NDJSON 流终态补全（`done_reason`） | `server_test.go` | 中 |
| 管理页稳定性摘要增强 | `api.go`, `store.go` | 中 |
| 大请求 soak 测试数据（20 轮 × 2 provider） | `.bin/large-request-matrix/` | 低 |

**审查意见**：

✅ **正确设计**：`recovery_policy.go` 将分散在 `server.go` 中的判断集中到一处：
- `shouldStopCandidateFallback`：决定哪些错误码必须停止候选切换
- `canAttemptAlternateChatMode`：统一流式/非流式互切的准入条件
- `markWrittenStreamFailure`：半截流（下游已开始写 SSE 后上游断开）的记账逻辑

✅ **正确原则**：`shouldStopCandidateFallback` 包含了 `upstream_no_response` 和 `upstream_stream_interrupted`，确保"请求可能已提交"的场景不会被 fallback 到第二个 provider 重复发送。

✅ **测试矩阵完备**：`TestRecoveryBoundaryMatrix` 用表驱动测试锁住了所有 stop 和不 stop 的类别，修改边界需要显式改测试。

⚠️ **注意点**：`markWrittenStreamFailure` 设置 `responseWriter.statusCode = 502` 但不调用 `WriteHeader`——依赖 `loggingMiddleware` 读取 `rw.statusCode` 写入日志。这是正确做法（HTTP 头已随 200 发出），但隐含了对 `responseWriter` 具体类型的依赖。`setResponseWriterStatus` 函数做了类型断言防护，这是好的。

## 3. 协议转发核心架构评估

### 3.1 数据流完整度

```
客户端请求 → handleChatCompletions
  → 模型解析 (registry.ResolveCandidates)
  → applyDefenseCandidatePolicy (截断为 1 个候选)
  → for each candidate:
      → transformRequest (参数归一化)
      → applyProfileDefaults (模型 profile 默认值)
      → requestContextWithTimeout (超时预算)
      → [流式] handleStream → streamOpenAI / streamOllamaToOpenAI
      → [非流式] prov.ChatRaw / prov.Chat
      → [失败时] canAttemptAlternateChatMode (流式/非流式互切)
      → [失败时] shouldStopCandidateFallback (是否停止候选)
```

**评估**：数据流完整，每个阶段的错误处理都有明确的语义。候选策略从 `applyDefenseCandidatePolicy` 截断为 1 是合理设计——new-api/sub2api 内部已负责渠道轮换。

### 3.2 超时预算模型

```
客户端请求
  └─ requestContextWithTimeout(effectiveTimeout)
       ├─ effectiveTimeout = min(model.timeout_seconds, client_timeout_budget_seconds)
       └─ providerOperationContext
            ├─ 如果 parent 已有 deadline → 继承
            └─ 否则 → context.WithTimeout(parent, provider.Timeout)
```

**评估**：
- `client_timeout_budget_seconds` 默认 90s 作为安全阀，防止模型超时设置过大导致资源泄漏 ✅
- `providerOperationContext` 不覆盖已有 deadline ✅
- `http.Client.Timeout = 0`（在 `doChatHTTPRequest` 中显式置零），避免 Go HTTP client 的独立超时与上层 deadline 产生竞态 ✅

### 3.3 错误传播链

```
provider.ChatRaw/ChatStream 错误
  ├─ providerHTTPError (HTTP 状态码错误)
  ├─ upstreamTransportError (传输层错误，含 httptrace stage)
  └─ upstreamAttemptsError (包装最终错误 + 所有尝试明细)
       └─ proxy 层通过 provider.UpstreamAttempts(err) 提取
            ├─ newAttemptDiagnostic → 外层 category
            └─ newUpstreamAttemptDiagnostics → 内层 category
                 └─ classifyUpstreamAttempt → stage 修正
```

**评估**：
- 错误类型通过 `errors.As` 解包，不依赖具体 provider 类型 ✅
- `upstreamAttemptsError` 保持原错误链（`Unwrap` 返回原始错误），不破坏既有 `errors.Is` 逻辑 ✅
- `classifyUpstreamAttempt` 有 **两阶段修正**：
  1. HTTP 5xx → 直接标为 `upstream_server_error`
  2. `network_error` + `waiting_response_headers` → 升格为 `upstream_no_response`
  这是关键设计，消除了"连接失败"与"上游不响应"的混淆 ✅

## 4. 潜在风险与改进建议

### 4.1 风险：低（已有防护）

| 风险 | 现有的防护 | 评级 |
|------|-----------|------|
| 字符串匹配脆弱性 | `isRetryableConnectionBreak` 只在连接建立前阶段调用 | 🟢 低 |
| `responseWriter` 类型依赖 | `setResponseWriterStatus` 做了类型断言 | 🟢 低 |
| 内层 attempt 错误文本包含敏感信息 | `newUpstreamAttemptDiagnostics` 调用 `sanitizeDiagnosticMessage` | 🟢 低 |
| `UpstreamAttempt.Error` 保存了完整错误文本 | proxy 层调用 `sanitizeDiagnosticMessage` 后才写入日志/HTTP 头 | 🟡 中低 |

关于最后一点：`provider.UpstreamAttempt.Error` 字段保存了 `err.Error()` 的完整文本（可能包含 URL/IP 地址），但在 `diagnostic_error.go:newUpstreamAttemptDiagnostics` 中通过 `sanitizeDiagnosticMessage` 脱敏后才进入 proxy 诊断层。如果未来有其他代码直接读取 `UpstreamAttempt.Error` 绕过脱敏，需要警惕。建议在 `newUpstreamAttempt` 中就做基本脱敏，消除这个隐患。

### 4.2 改进建议

1. **（低优先级）`UpstreamAttempt.Error` 预脱敏**
   - 位置：`provider.go:newUpstreamAttempt`
   - 建议：对 `attempt.Error` 做与 `sanitizeDiagnosticMessage` 相同的 token 脱敏
   - 理由：防御纵深，即使未来代码绕过 proxy 层直接读取也不会泄露

2. **（低优先级）`isRetryableConnectionBreak` 优先使用类型判断**
   - 当前实现：先检查 `errors.Is(err, io.EOF)` 等，再 fallback 到字符串匹配
   - 建议：增加对 `*net.OpError` 的检查（如 `opError.Op == "dial"`），减少字符串匹配的依赖
   - 理由：`net.OpError` 已经有结构化的操作类型字段，比解析错误文本更可靠

3. **（建议）增加 `provider_test.go` 中对 httptrace 阶段的单元测试**
   - 当前 `TestOpenAIProviderTimeoutReportsWaitingResponseHeaders` 是集成测试风格
   - 建议：增加纯单元测试验证 `upstreamHTTPTrace` 的阶段前进逻辑（尤其是 GetConn 重置、并发安全）

4. **（建议）`openAIProviderMaxAttempts` 常量可配置化**
   - 当前硬编码为 3，已满足需求
   - 如果未来需要为不同 provider 设置不同重试次数，可考虑移到 provider 配置中

## 5. 与行业最佳实践的对比

| 实践 | 本项目的做法 | 行业参考 |
|------|-------------|---------|
| 非幂等 POST 重试边界 | httptrace 阶段机，写请求后不重试 | Stripe API 使用 Idempotency-Key；OpenAI SDK 在连接层重试但不重放已提交请求 |
| 流式响应错误处理 | `markWrittenStreamFailure` 记内部 502 + 错误码，保持客户端 200 | SSE 协议限制，行业普遍采用响应头/日志异步记账 |
| 上游错误分类 | 两层分类（HTTP 状态码 → httptrace 阶段修正 → 业务文本匹配） | OpenAI 官方节点用状态码 + error.type；LangChain 用异常类型映射 |
| 超时预算 | 模型超时 + 全局安全阀，继承 parent deadline | 标准做法：上游超时应由调用方控制，代理层不独立计时 |
| API Key 安全 | 不保存 URL/Header/Body 到诊断日志；sanitize 正则脱敏 | OWASP 最佳实践：日志中脱敏凭据 |
| 稳定性观测 | recent_stability 仅展示不参与路由 | 12-factor app：观测与决策解耦 |

**结论**：本项目的做法与行业最佳实践高度一致，在非幂等 POST 重试边界上的处理甚至比很多 SDK 更严谨。

## 7. 总结

这 4 个提交构成了协议转发稳定性的一次**系统性加固**。核心设计理念——"非幂等 POST 一旦写出就不再由代理重放"——是正确且必要的。

### 做得特别好的地方

1. **httptrace 阶段机**：是正确区分"连接失败"和"上游不响应"的唯一可靠手段，实现简洁高效
2. **两层尝试诊断**：proxy 候选切换 vs provider 内部重试的分离，解决了"请求是否被放大"这个长期无法回答的问题
3. **边界集中管理**：`recovery_policy.go` 让所有恢复决策可审计、可测试
4. **文档与代码一致性**：`docs/38-42` 与代码实现高度一致，踩坑记录翔实

### 下一步建议

1. 在 soak 测试中持续积累 `upstream_no_response` 的出现模式，量化"大请求（>400KB）vs 普通请求"的失败率差异
2. 观察 `recent_stability` 在生产环境中的数据，如果发现某 provider/model 组合的 `upstream_no_response` 率持续偏高（如 >10%），可作为上游渠道问题预警
3. 考虑在管理页增加"按请求体大小分桶的稳定性"视图，帮助用户直观看到大上下文请求的风险

**总体评级：生产就绪（Production Ready）**

## 补充：审查中执行的优化（2026-07-27）

审查后基于发现执行了以下具体代码优化，所有测试已通过。

### 优化 1：UpstreamAttempt.Error 预脱敏（provider 层）

**文件**：`internal/provider/provider.go`

**变更**：`newUpstreamAttempt` 中，`attempt.Error` 在存储前调用 `sanitizeUpstreamErrorText` 做基本脱敏：

- Bearer Token：`Bearer sk-xxx` → `Bearer <redacted>`
- OpenAI Key：`sk-xxx` → `sk-<redacted>`
- API Key 赋值：`api_key=xxx` → `api_key=<redacted>`

**理由**：防御纵深。proxy 层已有 `sanitizeDiagnosticMessage` 做二次脱敏，但若未来新增代码绕过 proxy 层直接读取 `UpstreamAttempt.Error`，provider 层的预脱敏可防止凭据泄露。

### 优化 2：isRetryableConnectionBreak 结构化类型判断增强

**文件**：`internal/provider/provider.go`

**变更**：
1. 新增 `*net.DNSError` 检查——DNS 解析失败时请求尚未建立 TCP 连接，直接可重试
2. 新增 `*net.OpError` 结构化判断（`isRetryableOpError`）：
   - `Op == "dial"` → 连接未建立，安全重试
   - 底层 syscall 错误类型判断（`isRetryableSyscallError`）：识别 connection refused/reset/broken pipe 等
3. **修复检查顺序**：将 `*net.DNSError` 和 `*net.OpError` 移到 `net.Error` 接口之前

**踩坑记录**：`*net.DNSError` 和 `*net.OpError` 都实现了 `net.Error` 接口（有 `Timeout()` / `Temporary()` 方法）。若将 `net.Error` 接口匹配放在具体类型匹配之前，DNS 错误（IsTimeout=false）和拨号错误（非超时）会被 `netErr.Timeout()` 检查错误地返回 false。Go 的 `errors.As` 按代码顺序匹配第一个可赋值的类型——**具体类型必须排在接口之前**。

### 优化 3：alternateChatModeFailure 保留初始错误链

**文件**：`internal/proxy/server.go`

**问题**：`alternateChatModeFailure` 使用 `%v` 格式化 `initialErr`，导致初始错误的 `UpstreamAttempts`（httptrace 阶段、HTTP 状态码等）无法被 `errors.As` 找到。

**修复**：新增 `alternateChatModeError` 类型，实现 `Unwrap() []error`（Go 1.20+），同时暴露 `initialErr` 和 `fallbackErr` 两个错误链。`errors.As` 按 `initial → fallback` 顺序搜索。

## 第二轮深度审查发现（2026-07-27）

第二轮审查对 `handleChatCompletions` 和 `handleOllamaChat` 的**每一条代码分支**进行了逐行追踪，

### 优化 4：非流式路径补全 `isClientGoneError` 提前返回

**文件**：`internal/proxy/server.go`

**问题**：流式路径在 `client_gone` 时有 `isClientGoneError` → return（让 `finalizeRequestStatus` 设置 499），
但非流式路径的 4 个错误处理位置缺少此检查，直接执行 `writeProxyDiagnosticError(502, ...)`。
这导致：
1. 客户端已断开，却向死连接写入 502 错误响应
2. `finalizeRequestStatus` 因检测到已设置的 502 + 错误码而跳过修正
3. 日志中 `client_gone` 的错误码对应错误的 HTTP 状态 502（应为 499）

**修复**：在以下 4 个位置增加 `isClientGoneError(err)` → `return` 提前返回：

| 位置 | 函数 | 路径 |
|------|------|------|
| 1 | `handleChatCompletions` | ChatRaw 非流式失败 |
| 2 | `handleChatCompletions` | typed provider 非流式失败 |
| 3 | `handleOllamaChat` | ChatRaw 非流式失败 |
| 4 | `handleOllamaChat` | typed provider 非流式失败 |
